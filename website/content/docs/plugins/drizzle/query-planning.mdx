title: Query planning
description: How the plugin decides what each field loads, and when a field costs a query of its own

This page describes how the plugin turns a GraphQL query into drizzle queries. You do not need it
to build a schema, but it is worth reading when a schema issues more queries than you expect.

## How fields get their data

A field either reads its data from a row that has already been loaded, or runs a query of its own.

A field's `select` is planned into the query of the nearest ancestor that runs one: a
`t.drizzleField`, a `t.relation`, a connection, or a [fallback query](./relations#fallback-queries). The field
then reads what it needs off the loaded row, without a query of its own. A field runs its own query
when its `resolve` queries drizzle directly, and when the plugin issues a fallback query for a
relation that is missing from the row.

A field can do both. A `t.drizzleField`, or any other field with a `select`, nested under one of
those ancestors has its `select` planned into the parent's row, and still runs its own query when
it resolves. The `select` describes the parent data it reads, and its own query produces the value
it returns.

Two selections of the same relation share a place in the query only when their arguments (`where`,
`orderBy`, `limit`, ...) match. When they differ, the first one planned wins, and the other is
loaded with a query of its own. A type-level `select` is planned before any field's selection, no
matter where they appear in the document, and fields are planned in the order they are selected.

A field-level `select` is merged into the same query as its siblings and the type-level selection,
rather than being kept separate for that field. Two fields that need the same relation with
different arguments can not both be answered from one row.

Selections can also be built by async callbacks, see [Async selections](#async-selections).

## Nested selections

A `select` function receives `nestedSelection`, which plans the selection beneath the field for the
field's own type. It returns the query config for that table, or a `many` config for a list field.
Any keys you pass in are kept as they were given, so `columns` passed to `nestedSelection` will
still narrow the parent shape:

```ts
builder.drizzleObject('users', {
  name: 'User',
  fields: (t) => ({
    latestPosts: t.field({
      type: [Post],
      select: (args, ctx, nestedSelection) => ({
        // what the query selects on the posts, limited to one
        with: { posts: nestedSelection({ limit: 1 }) },
      }),
      resolve: (user) => user.posts,
    }),
  }),
});
```

`nestedSelection(query, path, type)` takes two more arguments:

- `path`: a list of field names, for selecting a field nested under the field's type. A segment can
  also be written as `{ name, type }` to pin the implementation the field must be found under.
- `type`: a member of an interface or union, to read the selection as that type.

The `nestedSelection` function also carries the `path` and `segments` of the field being planned,
which are described under [Relation queries](./relations#relation-queries).

## Async selections

Selections are synchronous unless the schema opts in with `AsyncSelections: true`:

```ts
const builder = new SchemaBuilder<{
  DrizzleRelations: typeof relations;
  AsyncSelections: true;
}>({
  plugins: [DrizzlePlugin],
  drizzle: {
    client: db,
    getTableConfig,
    relations,
  },
});
```

With the opt-in, `select` functions, relation `query` callbacks, `relatedCount` `where` callbacks,
and the `select` and `query` callbacks of `drizzleConnectionHelpers` may be async. Without it they
are typed as synchronous, and an async callback is a type error.

The plugin still builds a single query. It waits for the callbacks, and merges what they return
after every synchronous selection, in document order. Schemas that do not use async callbacks are
unaffected, since no promise is created until a callback returns one.

```ts
builder.drizzleObject('users', {
  name: 'User',
  fields: (t) => ({
    posts: t.relation('posts', {
      query: async (args, ctx) => ({ where: { authorId: await ctx.currentUserId() } }),
    }),
    latestPosts: t.field({
      type: [Post],
      select: async (args, ctx, nestedSelection) => ({
        with: { posts: await nestedSelection({ limit: await ctx.previewSize() }) },
      }),
      resolve: (user) => user.posts,
    }),
  }),
});

builder.queryField('me', (t) =>
  t.drizzleField({
    type: 'users',
    // The plan is settled before the resolver runs, so `query()` never returns a promise
    resolve: (query, root, args, ctx) =>
      db.query.users.findFirst(query({ where: { id: ctx.userId } })),
  }),
);
```

Inside an async `select`, `await` the result of `nestedSelection` before adding it to the selection.
A selection that contains the promise itself will throw, and so will a `select` that returns while
a nested selection it started is still pending. Calling `nestedSelection` and discarding a
synchronous result is not detected, and the nested selection will not be loaded with the parent.

A helper's `getQuery` builds the query synchronously, and throws when a selection beneath the field
is async. Which selections are beneath the field depends on the document, so pass
`awaitSelections: true` in schemas that use async selections, and `await` what you get back:

```ts
select: async (args, ctx, nestedSelection) => ({
  with: {
    comments: await commentConnectionHelpers.getQuery(args, ctx, nestedSelection, {
      awaitSelections: true,
    }),
  },
}),
```

### What the opt-in asks of a schema

Anything the plugin builds for you keeps working with no changes. `t.relation`, `t.relatedCount`,
`t.drizzleField`, `t.drizzleConnection`, `t.relatedConnection` and the resolvers they generate
settle the plan before your resolver runs, so a schema built entirely from them can turn the opt-in
on and change nothing else.

The cost lands on the places where your own code asks the plugin for a query or a selection:

- `drizzleConnectionHelpers(...).getQuery`
- `nestedSelection`, the third argument of a field's `select`
- `nestedQuery`, the fourth argument of a `t.relatedField` `select`
- `mergeNestedSelection`, what a `pothosDrizzleSelect` field extension is handed

Once the opt-in is on, each of those either has to be updated — pass `awaitSelections: true` and
`await` the query, or `await` the nested selection — or it may throw. Which of them are affected
depends on whether any selection beneath that field is async, and that is a property of the
incoming document rather than of the call site, so reading the call site does not settle it.
Turning the opt-in on is a commitment to audit every one of them, and a schema that has none has
nothing to audit.

The two opt-ins are independent. The schema flag says whether a callback may be async;
`awaitSelections` says whether a particular `getQuery` call will await the query it builds, and
stays a per-call decision either way.

The throw is loud, and names the field and the option to pass. The alternative is a promise handed
back where the declared type says there is a query, which surfaces much further from its cause.

## Conflicting selections between variants

When a query selects two variants of one table for the same row, either with a fragment on each
under one field, or through a `t.variant` field, the plugin will throw a `PothosValidationError` if
their `select` options ask for the same relation with different arguments:

```
PothosValidationError: Type-level selections of Viewer and Admin conflict on relation "posts".
Move the relation arguments to a field-level select on one of the types.
```

The same applies to two variants defining the same `extras` key with different functions
(`... conflict on extra "lowercaseName"`). Both variants describe one row, so their `select`
options have to be merged into a single query, and unlike a field a type has nothing to fall back
to.

To fix this, move the relation with its arguments, or the extra, into the `select` of the field
that needs it on one of the variants. A field-level selection that conflicts with what the row
already holds falls back to a query for that field, rather than failing the request.
