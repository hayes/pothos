## Installing

```package-install
npm install --save @pothos/plugin-prisma-next
```

Install the Prisma framework and SQL family at the supported version, plus the runtime for your
database, such as `@prisma/orm-postgres` or `@prisma/orm-sqlite`. The plugin requires Node.js 24
or later.

```sh
npm install @prisma/orm-framework@8.0.0-rc.22 @prisma/orm-family-sql@8.0.0-rc.22 @prisma/orm-sqlite@8.0.0-rc.22
```

`@pothos/plugin-relay` and `@pothos/plugin-with-input` are optional. Install them to use nodes and
connections, or `t.prismaFieldWithInput`.

### Prisma CLI toolchain

The current `prisma` CLI bundles `@prisma/orm-toolchain@8.0.0-rc.21`, and `prisma contract emit`
fails against the rc.22 ORM packages. Override the toolchain version, for example with pnpm:

```json
{
  "pnpm": {
    "overrides": {
      "@prisma/orm-toolchain": "8.0.0-rc.22"
    }
  }
}
```

With the override, the scaffold's `temporal.UpdatedAtString` field does not emit; replace it in
the scaffolded contract. Don't downgrade the ORM packages instead: Prisma refuses to run with two
copies of the ORM installed.

## Configure the builder

Emit your contract with `prisma contract emit`. The JSON file is passed to the plugin, and its
`.d.ts` provides model, relation, and column types.

```ts
import SchemaBuilder from '@pothos/core';
import RelayPlugin from '@pothos/plugin-relay';
import prismaNextPlugin from '@pothos/plugin-prisma-next';
import sqlite from '@prisma/orm-sqlite/runtime';
import { contractFromJson } from '@prisma/orm-sqlite/static';

import contractJson from './prisma/contract.json' with { type: 'json' };
import type { Contract } from './prisma/contract';

const contract = contractFromJson<Contract>(contractJson);
const client = sqlite({
  contract,
  path: './app.db',
});
await client.connect();

const builder = new SchemaBuilder<{
  PrismaNextContract: Contract;
  Context: { db: typeof client };
}>({
  plugins: [RelayPlugin, prismaNextPlugin],
  relay: {},
  prismaNext: {
    contract,
  },
});
```

The client can also be created per request and passed in context:

```ts
import type { SqliteClient } from '@prisma/orm-sqlite/runtime';

const builder = new SchemaBuilder<{
  PrismaNextContract: Contract;
  Context: { db: SqliteClient<Contract> };
}>({
  plugins: [prismaNextPlugin],
  prismaNext: { contract },
});

builder.queryType({
  fields: (t) => ({
    users: t.prismaField({
      type: ['User'],
      resolve: (_root, _args, ctx) => ctx.db.orm.User,
    }),
  }),
});
```

## Plugin options

```ts
prismaNext: {
  contract,
  collections: (ctx) => ctx.db.orm,
  context: client.context,
  skipDeferredFragments: true,
  defaultConnectionSize: 20,
  maxConnectionSize: 100,
}
```

- `contract`: the contract from `contractFromJson`. Required.
- `collections`: Collections used to load selections a parent query couldn't include, such as
  conflicting to-one filters, deferred fragments, and rows returned from a plain `t.field`. Pass
  the client's `orm`, or a map of only the models that need it, such as
  `(ctx) => ({ User: ctx.db.orm.User, Post: ctx.db.orm.Post.where({ authorId: ctx.tenantId }) })`.
  Collections must be unpaginated. Rows are reloaded in batches by primary key, or a non-null
  unique key.
- `context`: the client's `context`. Lets object-valued columns, such as Temporal values, be used
  in cursors and loader identities through their column codecs.
- `skipDeferredFragments`: with `collections`, `@defer` fragments are left out of the initial
  query and loaded when executed. Set to `false` to load them eagerly. Without `collections`,
  they always load eagerly.
- `defaultConnectionSize` / `maxConnectionSize`: default and maximum page sizes, overridden per
  field with `defaultSize` and `maxSize`.

## Databases

- **PostgreSQL and SQLite** are supported.
- **MySQL** supports reads only. Its contracts have no aggregates, so `totalCount: true`,
  `t.relationCount`, and `t.relationAggregate` are type errors, and Prisma's writes require a
  `returning` capability MySQL lacks.
- **MongoDB** is not supported, and is rejected when the schema is built.

## Namespaced models

A model name that is unique in the contract is used as is. A name defined in several namespaces is
written `'ns.Model'`; its default GraphQL name is `ns_Model`. Use the same keys in a `collections`
map.

```ts
builder.prismaObject('billing.User', {
  fields: (t) => ({
    id: t.exposeID('id'),
  }),
});
```

## Transactions

Pothos does not create transactions. To run a mutation's queries in one, execute GraphQL inside
the transaction callback and pass the transaction as `ctx.db`. Type `db` with the query members
the client and transactions share:

```ts
import type { SqliteQueryMembers } from '@prisma/orm-sqlite/runtime';

type Context = { db: SqliteQueryMembers<Contract> };
```

```ts
const result = await client.transaction(async (tx) => {
  const result = await graphql({
    schema,
    source,
    contextValue: { db: tx },
  });
  if (result.errors?.length) {
    throw result.errors[0];
  }
  return result;
});
```

GraphQL reports errors in the result rather than rejecting, so throw to roll back. The
`collections` option must return Collections from the same transaction; the plugin can't detect a
provider that uses a different client. Finish executing, including deferred results, before the
callback returns.

## TypeScript

- Set `PrismaNextContract` on the builder's types. Without it, model names autocomplete to a
  message explaining what to configure.
- With `skipLibCheck: false`, install the optional `@pothos/plugin-relay` and
  `@pothos/plugin-with-input` peers for their types.
- Temporal columns need global Temporal types. On TypeScript versions without them, install
  `temporal-spec` and add `import type {} from 'temporal-spec/global'`.
