## Installing

The plugin requires Node.js 22.18 or a later 22.x release, or Node.js 24 or later. The Prisma CLI
requires `^22.18.0 || ^24.11.0 || >=26.0.0`, so on Node.js 24 use 24.11 or later. SQLite also needs
Node.js 22.20 or later: on 22.18 and 22.19, `prisma db init` and queries fail with `Database error
while reading contract marker`.

`@pothos/plugin-prisma-next` cannot be used in the same program as `@pothos/plugin-prisma`: both
add `prismaObject`, `prismaField` and the other `prisma*` methods to the builder. Importing both
throws at runtime, and their type declarations conflict: TS2717, or with `skipLibCheck: true`,
errors in your own code such as a missing `prisma` builder option.

### Prisma CLI

Start from a `package.json` that sets `"type": "module"`. In a new project, run `npm init -y` and
`npm pkg set type=module`, or `pnpm init` and add `"type": "module"` if it isn't there.

The CLI is versioned separately from the ORM packages. The steps below were checked with
`prisma@8.0.0-rc.29` against the rc.22 ORM packages. That CLI depends on
`@prisma/orm-toolchain@8.0.0-rc.21`, which scaffolds a contract rc.22 can't read
(`PSL_UNRESOLVED_REFERENCE`), so override the toolchain version before installing the CLI. With
npm, add this to `package.json`:

```json
{
  "overrides": {
    "@prisma/orm-toolchain": "8.0.0-rc.22"
  }
}
```

With pnpm, create `pnpm-workspace.yaml`. pnpm 12 ignores overrides in `package.json`, and without
`strictDepBuilds: false` its installs exit with an error about the esbuild and workerd build
scripts, which these steps don't need:

```yaml
overrides:
  '@prisma/orm-toolchain': 8.0.0-rc.22
strictDepBuilds: false
```

Yarn uses `resolutions` with the same entry as npm. Don't downgrade the ORM packages instead,
because Prisma refuses to run with two copies of the ORM installed. If the CLI is already
installed, run `npm install` or `pnpm install` after adding the override.

Then install the CLI. The plugin's peer dependencies are exact versions, so pin Prisma packages
with `--save-exact`:

```package-install
npm install --save-dev --save-exact prisma@8.0.0-rc.29 @prisma/cli-engine@0.9.0
```

### PostgreSQL

Scaffold the project. `orm init` writes a contract, a `prisma.config.ts`, a `tsconfig.json`, and a
`src/prisma/db.ts` that creates the client. `--skip-install` stops it from installing
`prisma@latest` and the latest `@prisma/orm-postgres`, which would replace the pinned versions.
With pnpm, run this and the other `npx` commands on this page with `pnpm exec` in place of `npx`.

```sh
npx prisma orm init --target postgres --authoring psl --skip-install
```

Install the ORM packages at the supported version, and the rest of the dependencies:

```package-install
npm install --save-exact @prisma/orm-framework@8.0.0-rc.22 @prisma/orm-family-sql@8.0.0-rc.22 @prisma/orm-postgres@8.0.0-rc.22
```

```package-install
npm install --save @pothos/core @pothos/plugin-prisma-next @pothos/plugin-relay graphql dotenv
```

```package-install
npm install --save-dev @types/node tsx typescript
```

`@pothos/plugin-relay` is only needed for nodes and connections, and the builder below uses it.
`@pothos/plugin-with-input` is optional, for `t.prismaFieldWithInput`.

Copy the example environment file, and set `DATABASE_URL` in `.env` to your database, which must
be PostgreSQL 15 or later:

```sh
cp .env.example .env
```

Emit the contract and create its tables in the database:

```sh
npx prisma contract emit
npx prisma db init
```

### SQLite

Follow these steps instead of the PostgreSQL ones. `orm init` doesn't scaffold SQLite, so write
the files yourself. `DATABASE_URL` isn't used.

`prisma.config.ts`:

```ts
import { definePrismaConfig } from '@prisma/cli-engine';
import { defineConfig as ormConfig } from '@prisma/orm-sqlite/config';

export default definePrismaConfig({
  orm: ormConfig({
    contract: './src/prisma/contract.prisma',
    db: { connection: './app.db' },
  }),
});
```

`src/prisma/contract.prisma`, which needs the `// use prisma-8` line:

```prisma
// use prisma-8

model User {
  id    Int    @id @default(autoincrement())
  email String @unique
  posts Post[]
}

model Post {
  id       Int    @id @default(autoincrement())
  title    String
  author   User   @relation(fields: [authorId], references: [id])
  authorId Int
}
```

`src/prisma/db.ts`:

```ts
import sqlite from '@prisma/orm-sqlite/runtime';
import { contractFromJson } from '@prisma/orm-sqlite/static';
import type { Contract } from './contract.d';
import contractJson from './contract.json' with { type: 'json' };

export const contract = contractFromJson<Contract>(contractJson);

export const db = sqlite({ contract, path: './app.db' });
```

`tsconfig.json`:

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "preserve",
    "moduleResolution": "bundler",
    "resolveJsonModule": true,
    "strict": true,
    "skipLibCheck": true,
    "noEmit": true,
    "types": ["node"]
  }
}
```

Install the dependencies, emit the contract, and create the tables:

```package-install
npm install --save-exact @prisma/orm-framework@8.0.0-rc.22 @prisma/orm-family-sql@8.0.0-rc.22 @prisma/orm-sqlite@8.0.0-rc.22
```

```package-install
npm install --save @pothos/core @pothos/plugin-prisma-next @pothos/plugin-relay graphql
```

```package-install
npm install --save-dev @types/node tsx typescript
```

```sh
npx prisma contract emit
npx prisma db init
```

## Configure the builder

Pass the client from `src/prisma/db.ts` to the plugin. Model, relation, and column types come
from the emitted contract, so run `prisma contract emit` after changing the contract.

Create `src/schema.ts`:

```ts
import SchemaBuilder from '@pothos/core';
import RelayPlugin from '@pothos/plugin-relay';
import prismaNextPlugin from '@pothos/plugin-prisma-next';
import { contract, db } from './prisma/db';

const builder = new SchemaBuilder<{
  PrismaNextContract: typeof contract;
  Context: { db: typeof db };
}>({
  plugins: [RelayPlugin, prismaNextPlugin],
  relay: {},
  prismaNext: { client: db },
});

builder.prismaObject('User', {
  fields: (t) => ({
    id: t.exposeID('id'),
    email: t.exposeString('email'),
  }),
});

builder.queryType({
  fields: (t) => ({
    users: t.prismaField({
      type: ['User'],
      resolve: (_root, _args, ctx) => ctx.db.orm.public.User,
    }),
  }),
});

export const schema = builder.toSchema();
```

Create `src/index.ts`:

```ts
import { graphql } from 'graphql';
import { db } from './prisma/db';
import { schema } from './schema';

await db.orm.public.User.create({ email: `${Date.now()}@example.com` });

const result = await graphql({
  schema,
  source: '{ users { id email } }',
  contextValue: { db },
});

console.log(JSON.stringify(result));
await db.close();
```

On SQLite, write `db.orm.User` in place of `db.orm.public.User` in both files. Run it:

```sh
npx tsx src/index.ts
```

A PostgreSQL client groups collections by schema, as in `ctx.db.orm.public.User`. The other pages
use a SQLite client, where the same collection is `ctx.db.orm.User`.

To load through a client chosen per request, such as a transaction, pass a function of the
context as `client`. A transaction has no `context` of its own, so pass the `context` of the client
it comes from as well. The plugin reads the contract from it when the schema is built, and the
column codecs for cursors and node IDs when a request runs:

```ts
import type { PostgresQueryMembers } from '@prisma/orm-postgres/runtime';

const builder = new SchemaBuilder<{
  PrismaNextContract: typeof contract;
  Context: { db: PostgresQueryMembers<typeof contract> };
}>({
  plugins: [prismaNextPlugin],
  prismaNext: {
    client: (ctx) => ctx.db,
    context: db.context,
  },
});

builder.queryType({
  fields: (t) => ({
    users: t.prismaField({
      type: ['User'],
      resolve: (_root, _args, ctx) => ctx.db.orm.public.User,
    }),
  }),
});
```

## Plugin options

```ts
prismaNext: {
  client: db,
  skipDeferredFragments: true,
  defaultConnectionSize: 10,
  maxConnectionSize: 50,
  filterConnectionTotalCount: true,
}
```

- `client`: the Prisma client, or `(ctx) => client` together with `context`. Required. The
  plugin also uses it to [load fields a parent query couldn't
  include](./relations#loading-without-a-parent-query) and for `node(id:)`.
- `skipDeferredFragments`: leaves `@defer` fragments out of the initial query and loads them when
  they execute. Defaults to `true`. Set it to `false` to load them eagerly. A model without an
  [identity](./relations#loading-without-a-parent-query) can't be reloaded, so its deferred
  fields need `false`.
- `defaultConnectionSize` / `maxConnectionSize`: default and maximum page sizes, 20 and 100 when
  unset. Fields override them with `defaultSize` and `maxSize`, which can also be
  `(args, ctx) => number`. As in Pothos core, they aren't validated: use positive integers.
- `filterConnectionTotalCount`: a `relatedConnection`'s `totalCount` counts the rows matching its
  `query.where`. Set to `false` to count every related row.

A context object is required: execute every operation with one, such as `contextValue: {}`,
because the plugin keeps per-request state on it. An operation without one fails, and the plugin
doesn't check for it first.

The plugin relies on its types and doesn't check again at runtime what they already enforce, such as
model keys or the shape of a `query`. Rules the types can't express, such as a node's `id.field`
covering a key, fail when the schema is defined or built.

A callback that runs while a field is planned fails only that field: a field's `select`, a
relation's or connection's `query`, a `where` given the field's arguments, a connection's `orderBy`
or page size, and an invalid cursor or page size from a client. The query the field was planned
into still runs for its other fields. A `where` or `orderBy` callback given the model's columns,
and an option the ORM rejects, such as a negative `limit`, fail the query it belongs to and every
field that query loads.

Keep these callbacks pure: compute the result from their arguments and context only, without side
effects. They run when a query is planned, not per row, and the plugin decides how often: once per
selection of the field however many parents it loads, again when a field reloads its parent, and
for a `@defer` fragment only when it executes.

## Errors

Errors for a client's bad input, such as an invalid cursor or node ID, are `PothosValidationError`s
with messages safe to show, such as `Invalid cursor.`. Errors in the schema's own code, such as a
field that needs its parent reloaded on a model without an identity, are plain `Error`s whose
messages name models and columns for your logs. Enable error masking on your server, as GraphQL
Yoga does by default, so clients see a generic message for those. A `PothosValidationError` is a
`GraphQLError`, which masking passes through.

## Databases

PostgreSQL and SQLite are supported. MySQL supports reads only: its contracts have no aggregates,
so `totalCount: true`, `t.relationCount`, and aggregates in a `select` are type errors, and Prisma's
writes need a `returning` capability MySQL lacks. MySQL isn't tested in CI. MongoDB contracts are
a type error.

## Namespaced models

A contract with one namespace uses bare model keys, such as `'User'`. In a contract with several
namespaces, every key is written `'ns.Model'`, even when only one namespace defines that model. A
bare `'User'` isn't a key there, and neither is `'public.User'` in a contract with one namespace.

```ts
builder.prismaObject('billing.User', {
  fields: (t) => ({
    id: t.exposeID('id'),
  }),
});
```

The default GraphQL name of a type is the bare model name, so `'billing.User'` is `User`. Registering
two models with the same name fails with a `Duplicate typename` error. Give one of them a `name`.
The model key still refers to it:

```ts
builder.prismaObject('auth.User', {
  name: 'AuthUser',
  fields: (t) => ({
    id: t.exposeID('id'),
  }),
});

builder.prismaObject('auth.Session', {
  fields: (t) => ({
    // Returns AuthUser.
    user: t.relation('user'),
  }),
});
```

## Transactions

Pothos does not create transactions. To run a mutation's queries in one, execute GraphQL inside
the transaction callback and pass the transaction as `ctx.db`. With
[`client: (ctx) => ctx.db`](#configure-the-builder), typed with `PostgresQueryMembers`, the
plugin's own loads use the same transaction. The plugin can't check that `ctx.db` is the
transaction, so a client on another connection loads outside it. Finish executing, including
deferred results, before the callback returns:

```ts
const result = await db.transaction(async (tx) => {
  const result = await graphql({
    schema,
    source,
    contextValue: { db: tx },
  });
  // GraphQL reports errors in the result rather than rejecting, so throw to roll back.
  if (result.errors?.length) {
    throw result.errors[0];
  }
  return result;
});
```

On SQLite, type `ctx.db` with `SqliteQueryMembers` from `@prisma/orm-sqlite/runtime` and run
the transaction with `db.transaction` the same way. SQLite allows one writer at a time, so while the
transaction is open a write through `db` rather than `tx` fails with `database is locked`, and a
read through `db` doesn't see the transaction's writes.

## TypeScript

- Set `PrismaNextContract` on the builder's types. Without it, model names autocomplete to a
  message explaining what to configure.
- Use `"moduleResolution": "nodenext"` or `"bundler"`. Prisma's ORM packages are ESM-only, so
  `node16` in a CommonJS project fails to typecheck the plugin's and the emitted contract's types.
- Temporal columns need global Temporal types. On TypeScript versions without them, install
  `temporal-spec` and add `import type {} from 'temporal-spec/global'`.
