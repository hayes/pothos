```package-install
npm install --save @pothos/plugin-prisma-next
```

Install the shared Prisma framework and SQL family at the supported version:

```sh
npm install @prisma/orm-framework@8.0.0-rc.22 @prisma/orm-family-sql@8.0.0-rc.22
```

Your application chooses its runtime, for example
`@prisma/orm-postgres@8.0.0-rc.22` or `@prisma/orm-sqlite@8.0.0-rc.22`.
The Pothos plugin does not choose a driver or inspect the database dialect.
Use Node.js 24 or later for this integration's supported runtime.

### Matching the Prisma CLI

Prisma numbers its CLI and ORM packages separately, so `prisma@8.0.0-rc.29` is not the same release
as `@prisma/orm-postgres@8.0.0-rc.22`. Today `prisma@latest orm init` installs this pair, but that
CLI still bundles `@prisma/orm-toolchain@8.0.0-rc.21`, and `prisma contract emit` fails with
`CLI.UNEXPECTED`. Until a CLI release ships the matching toolchain, override it. With pnpm:

```json
{
  "pnpm": {
    "overrides": {
      "@prisma/orm-toolchain": "8.0.0-rc.22"
    }
  }
}
```

With the override, the generated scaffold's `temporal.UpdatedAtString` also fails to emit, so replace
that field in the scaffolded contract. Don't downgrade the ORM packages to `8.0.0-rc.21` instead:
the plugin's peers are pinned, and Prisma refuses to run with two installed copies of the ORM
(`RUNTIME.MULTIPLE_ORM_COPIES`).

  install them only if you use Relay connections / `prismaFieldWithInput`.
</Callout>

## Setup

The plugin needs your Prisma contract at type-check time and at runtime.
Both come from the same JSON file emitted by `prisma contract emit`.

### Generate your contract

Run Prisma's contract emit step against your schema. The output is a JSON
file plus a `.d.ts` carrying the contract type. Check the
[Prisma ORM docs](https://www.prisma.io/docs/orm) for the up-to-date
command — this plugin treats the contract as the source of truth for model
names, relation names, column types, and FK metadata.

```sh
prisma contract emit
```

### Set up the builder

```ts
import SchemaBuilder from '@pothos/core';
import RelayPlugin from '@pothos/plugin-relay';
import prismaNextPlugin from '@pothos/plugin-prisma-next';
import sqlite from '@prisma/orm-sqlite/runtime';
import { contractFromJson } from '@prisma/orm-sqlite/static';

import contractJson from './prisma/contract.json' with { type: 'json' };
import type { Contract } from './prisma/contract';

// Connect the orm-client.
const contract = contractFromJson<Contract>(contractJson);
const client = sqlite({
  contract,
  path: './app.db',
});
await client.connect();

const builder = new SchemaBuilder<{
  // Threads the contract through every plugin method — model names,
  // relation names, column names, and row shapes are inferred from it.
  PrismaNextContract: Contract;
  Context: { db: typeof client };
}>({
  plugins: [RelayPlugin, prismaNextPlugin],
  relay: {},
  prismaNext: {
    contract,
  },
});
```

<Callout type="info">
  If you forget to set `PrismaNextContract` on `SchemaTypes`, autocomplete
  will point at a sentinel string explaining what to configure. The plugin's
  helper types collapse without a contract.
</Callout>

### Plugin options

Set on `builder.options.prismaNext`:

```ts
prismaNext: {
  contract,                    // required
  // Enables batched fallback loading. Pass the client's `orm`, or a map of only the models
  // that need a fallback, such as `{ User: ctx.db.orm.public.User }`.
  collections: (ctx) => ctx.db.orm,
  // The client's `context`. Lets object-valued columns such as Temporal values work in
  // cursors and fallback identities through their column codecs.
  context: client.context,
  skipDeferredFragments: true, // default with collections; false keeps eager loading
  defaultConnectionSize: 20,   // default `first:` for all connections
  maxConnectionSize: 100,      // hard cap on connection page size
}
```

`defaultConnectionSize` / `maxConnectionSize` flow through both
`t.prismaConnection` and `t.relatedConnection`. They're overridden by
per-field `defaultSize` / `maxSize` options when those are set.

### Databases

| Database | Status |
| --- | --- |
| PostgreSQL, SQLite | Tested for reads, writes, aggregates and connections |
| MySQL (preview) | Reads only. MySQL contracts have no aggregates, so `totalCount: true`, `t.relationCount` and `t.relationAggregate` are compile errors, and Prisma's `create`, `update` and `delete` need a `returning` capability MySQL lacks |
| MongoDB | Rejected when the schema is built. Prisma's Mongo Collections have no `combine`, cursor or aggregates, and don't apply include refinements |

`postgresServerless().connect()` is tested against a local PostgreSQL server; Workers and
Hyperdrive themselves aren't run.

### Models in several namespaces

A model name that's unique in the contract stays bare. One defined in several namespaces is
written `'ns.Model'`, and autocompletes that way. Its default GraphQL type name is `ns_Model`, and
its relations stay within its namespace:

```ts
builder.prismaObject('billing.User', {
  fields: (t) => ({
    id: t.exposeID('id'),
  }),
});
```

A bare name that is ambiguous, or a qualified name for a unique model, is a type error, and throws
when the schema is built.

## TypeScript integration

The plugin's declarations include optional Relay and with-input interfaces, as
in the other Pothos ORM plugins. Runtime imports do not require those plugins.
Projects that check dependency declarations with `skipLibCheck: false` should
install both optional type peers. They need not enable either plugin at runtime.

Use the global Temporal declarations expected by your chosen Prisma codecs. With
TypeScript versions that do not supply them in `lib`, applications can install
`temporal-spec` and include `import type {} from 'temporal-spec/global'`. The
runtime Temporal implementation/polyfill is a separate application dependency.
Pothos itself does not load Temporal or select database codecs.

## Selection and transaction lifetime

A resolver can also return a row built by hand or one that no longer exists, such as the result
of a delete, from a plain `t.field`. Fields satisfied by the row's own columns resolve without a
query. With `collections` configured, a field needing anything else loads it by the row's identity,
and fails on its own if that row is gone.

Return the unexecuted Collection from `t.prismaField` and
`t.prismaFieldWithInput`. The plugin applies the initial selection plan before
executing it. Already-materialized root results are rejected because their
types cannot prove that the runtime GraphQL selection was loaded.

Configure `collections` with a model-name map or a context callback returning that
map. A partial map is allowed, but every model that needs a fallback must have an
entry. For example, `collections: (ctx) => ({ User: ctx.db.orm.User, Post:
ctx.db.orm.Post.where({ tenantId: ctx.tenantId }) })` preserves application filters.
Model names must be globally unique.

The loader reloads parent rows in batches using their primary key, or a non-null
unique key when no primary key is available. Identity columns are selected
automatically. Provider Collections must be unpaginated: no `limit`, `offset`, or
`cursor`. If application filters exclude a parent, its field receives a loading
error. Opaque object identity codecs are not yet supported; built-in scalar,
Date, byte-array, and Decimal identities are supported.

With `collections`, incompatible to-one selections load in separate compatible
batches and deferred fields load when executed. Set `skipDeferredFragments:
false` to retain eager deferred loading. Without `collections`, deferred data
loads eagerly and incompatible to-one selections fail during planning. Register
the `@defer` directive on the schema and use an incremental GraphQL executor to
receive deferred payloads.

Execute GraphQL while a transaction-bound client is still active when you want
queries, related selections, node loads, and counts in that transaction. Do not
return an unexecuted Collection from a transaction callback and then execute it
after the callback has ended. The `collections` provider must return Collections
bound to that same live transaction. Consume incremental results before ending
the transaction as well. Pothos does not create transactions or change their
isolation policy.

For an atomic mutation operation, execute GraphQL inside the application's
transaction callback and explicitly handle execution errors:

```ts
const result = await client.transaction(async (tx) => {
  const result = await graphql({
    schema,
    source,
    contextValue: { db: tx },
  });
  if (result.errors?.length) {
    throw result.errors[0];
  }
  return result;
});
```

Here, resolvers use `ctx.db.orm` and the `collections` callback returns model
Collections from that same client. GraphQL normally resolves with an `errors`
array rather than rejecting its promise; returning that result from the
transaction callback can commit writes made before the error. Choose the rollback
policy in application code. Serial mutation fields can read earlier writes, and
each field's nested result finishes before the next mutation field starts.

## Loading the orm-client per request

The example above uses a single shared `client`. You can also keep the
client in context if you need per-request isolation (e.g. one connection
pool per tenant):

```ts
const builder = new SchemaBuilder<{
  PrismaNextContract: Contract;
  Context: { db: ReturnType<typeof sqlite<Contract>> };
}>({
  plugins: [prismaNextPlugin],
  prismaNext: { contract },
});

// Resolvers reach the client via `ctx.db.orm.<Model>`:
builder.queryType({
  fields: (t) => ({
    users: t.prismaField({
      type: ['User'],
      resolve: (_root, _args, ctx) => ctx.db.orm.User,
    }),
  }),
});
```
