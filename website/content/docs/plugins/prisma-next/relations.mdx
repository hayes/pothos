---
title: Relations
description: Adding relations to Prisma-backed types
---

`t.relation` exposes a relation from the contract:

```ts
builder.prismaObject('User', {
  fields: (t) => ({
    id: t.exposeID('id'),
    email: t.exposeString('email'),
    posts: t.relation('posts'),
  }),
});

builder.prismaObject('Post', {
  fields: (t) => ({
    id: t.exposeID('id'),
    title: t.exposeString('title'),
    author: t.relation('author'),
  }),
});
```

Relations are loaded with `.include(...)` on the parent's Collection, so
`{ me { posts { author { id } } } }` runs as one Collection call.

To-many relations are non-null lists. To-one relations are non-null when their foreign key is
non-null and they have no `query` or variant `type` that could filter the row out. Pass `nullable`
to override.

## Filtering and sorting

`query` accepts `{ where, orderBy, limit, offset }`, or a function of the field's arguments and
context returning one. A to-one relation's `query` takes only `where`.

```ts
posts: t.relation('posts', {
  args: { oldestFirst: t.arg.boolean() },
  query: (args) => ({
    orderBy: (post) => (args.oldestFirst ? post.createdAt.asc() : post.createdAt.desc()),
  }),
}),
```

For a to-many relation, the function can instead return a function that refines the relation's
collection, for example to apply a fragment:

```ts
const published = db.orm.Post.fragment((posts) => posts.where({ published: 1 }));

posts: t.relation('posts', {
  query: () => (posts) => posts.with(published).orderBy((post) => post.createdAt.desc()),
}),
```

With `AsyncSelections: true` in the builder's types, the function can be async.

## Counts and other aggregates

```ts
builder.prismaObject('User', {
  fields: (t) => ({
    postCount: t.relationCount('posts'),
    publishedPostCount: t.relationCount('posts', { where: { published: 1 } }),
    postCountByState: t.relationCount('posts', {
      args: { published: t.arg.int({ required: true }) },
      where: (args) => ({ published: args.published }),
    }),
  }),
});
```

`where` takes the same values as a relation's `query.where`, or a function of the arguments and
context returning one. A count is always a non-null `Int`; to hide it from some users without
nulling the parent, use a nullable field with a `select`, as below.

For other aggregates, use a field `select`. The function receives the relation's Collection, and
each key it returns is added to the parent row. Keys must be literal strings:

```ts
builder.prismaObject('User', {
  fields: (t) => ({
    latestPostTitle: t.field({
      type: 'String',
      nullable: true,
      select: { posts: { orderBy: (post) => post.createdAt.desc(), limit: 1 } },
      resolve: (user) => user.posts[0]?.title ?? null,
    }),
    postStats: t.field({
      type: 'String',
      select: {
        posts: (posts) => ({ total: posts.count(), score: posts.sum('score') }),
      },
      resolve: (user) => `${user.total} posts, score ${user.score}`,
    }),
  }),
});
```

## Many-to-many

Relations defined with `rel.manyToMany({ through, from, to })` work with `t.relation`. To expose
columns on the junction, model it as its own model and use two relations.

## Loading without a parent query

A row returned from a plain `t.field` must include its primary key and the columns and to-one
relations of the type's `select`. Other selections are loaded through the plugin's `client`,
batched across parents. `typeof User.$inferType` names this row type.

Rows are reloaded by their primary key, or the first non-null unique key if there isn't one (return
the whole row for such a model). A model with neither can't be reloaded, so its fields must be
loaded by the parent query.
