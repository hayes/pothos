Nodes require the [Relay plugin](./setup#installing). [Connections](./connections) covers
pagination.

## Define a node

`builder.prismaNode` takes the same options as `builder.prismaObject`, plus an `id`:

```ts
builder.prismaNode('Post', {
  id: { field: 'id' },
  fields: (t) => ({
    title: t.exposeString('title'),
    author: t.relation('author'),
  }),
});
```

- `id.field`: a column, or a list of columns. They must include a complete non-null primary or
  unique key; otherwise the schema build fails.
- `id.parse` / `id.resolve`: custom serialization of the ID. `parse` turns the ID back into the
  key's values. `resolve` changes the encoded value, so it requires `parse`: the types reject it
  alone, since `node(id:)` would find no row.
- Other `id` options, such as `description`, `extensions` or another plugin's `authScopes`, are
  passed to the ID field.
- `collection`: a function of the context returning the Collection nodes load from. Defaults to
  the model's collection on the plugin's `client`. See
  [Filter node lookups](#filter-node-lookups).

```ts
builder.prismaNode('Comment', {
  id: {
    field: 'id',
    resolve: (comment) => `comment:${comment.id}`,
    parse: (id) => id.slice('comment:'.length),
  },
  fields: (t) => ({ body: t.exposeString('body') }),
});
```

By default IDs encode the key columns with the client's column codecs, and
`t.arg.globalID({ for: ref })` receives the decoded values.

An ID column must hold the value it is read as. A Postgres timestamp read as a JavaScript `Date`
keeps milliseconds, so an `id.field` with a precision above 3, or none, is a schema build error;
bare `DateTime` is `timestamptz(3)` and works. Use `TimestamptzTemporal` for finer timestamps.

`node` and `nodes` lookups of one type are batched into one query, with the selection applied,
including aliased `node` fields whose selections can load together.

## Filter node lookups

`collection` runs for each batch of lookups, so it can use the request's client and filter by the
request's values:

```ts
builder.prismaNode('Post', {
  id: { field: 'id' },
  collection: (ctx) => ctx.db.orm.Post.where({ authorId: ctx.viewerId }),
  fields: (t) => ({ title: t.exposeString('title') }),
});
```

`node` and `nodes` return `null` for a row the filter excludes.

Return the collection filtered but otherwise unshaped: one with `limit()`, `offset()`, `cursor()`
or `include()` is rejected, since the plugin pages the lookups and includes what the query
selects. On a [variant](./interfaces) model, return it narrowed with `orm.Base.variant(value)`.

`collection` applies only to `node` and `nodes` lookups, so it isn't access control. Rows reached
through `t.relation`, `t.relatedConnection`, `prismaField` or `prismaConnection` don't pass through
it, and neither do reloads of a parent row's missing selections, which read the model's collection
on the plugin's `client`. Use auth checks on the type to restrict rows everywhere: a function
`client` restricts rows only if the client it returns is scoped, and a resolver can still return a
build-time client.

## Several node types for one model

Use `isTypeOf` to decide which type a row belongs to. It can only read columns in the type's
`select`:

```ts
builder.prismaNode('Post', {
  variant: 'DraftPost',
  id: { field: 'id' },
  select: ['published'],
  isTypeOf: (post) => post.published === 0,
  fields: (t) => ({ title: t.exposeString('title') }),
});
```
