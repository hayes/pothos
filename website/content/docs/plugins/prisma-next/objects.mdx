`builder.prismaObject` defines a GraphQL object type for a model in your contract.

## Define a type

Pass the model name and the usual object type options. Column types come from the contract.

```ts
builder.prismaObject('User', {
  fields: (t) => ({
    id: t.exposeID('id'),
    email: t.exposeString('email'),
  }),
});
```

The GraphQL type is named after the model. Pass `name` to call it something else.

To add fields to a type elsewhere, use [`prismaObjectFields`](#adding-fields). To expose the same
model as another GraphQL type, define a [`variant`](./variants) or a
[`prismaInterface`](./interfaces).

## Selections

A field that reads columns it doesn't expose, or data from a relation, declares them with `select`.
The plugin then loads them along with the rest of the query.

```ts
builder.prismaObject('User', {
  // Loaded whenever a User is queried
  select: { firstName: true, lastName: true },
  fields: (t) => ({
    fullName: t.string({
      resolve: (user) => `${user.firstName} ${user.lastName}`,
    }),
    // Loaded only when emailDomain is queried
    emailDomain: t.string({
      select: ['email'],
      resolve: (user) => user.email.split('@')[1] ?? '',
    }),
    publishedPostCount: t.int({
      select: {
        posts: (posts) => ({ publishedCount: posts.where({ published: 1 }).count() }),
      },
      resolve: (user) => user.publishedCount,
    }),
  }),
});
```

A `select` on the type is loaded whenever the type is queried, and every field can read it. A
`select` on a field is loaded only when that field is queried. The primary key is always loaded.

A `select` accepts:

- Columns: `{ email: true }` or `['email']`.
- Relations: `{ posts: true }`.
- Filtered or sorted relations: `{ posts: { where: { published: 1 }, orderBy: { createdAt: 'desc' }, limit: 5 } }`.
  `where` also takes the ORM's predicate callback, and `orderBy` its selectors, as in `t.relation`'s
  `query`.
- A `select` of the relation's rows, in the same form: `{ comments: { limit: 5, select: { post: true } } }`.
- `type`, a ref or model name of a [variant](./interfaces#native-inheritance) of the relation's
  target, which loads only that variant's rows: `{ tasks: { type: Bug } }`.
- In a field's `select` only, counts and aggregates of a to-many relation:
  `{ posts: (posts) => ({ postCount: posts.count() }) }`. Each key (`postCount`) is added to the
  row, so don't reuse a column or relation name.

A to-one relation takes only `type` and `select`. Read aggregates in a resolver; `t.expose*` only
works on columns.

Every type of a model reads the same rows for each relation a type-level `select` names, so the
type-level `select`s of one model, including its [variants](./variants) and
[interfaces](./interfaces), must write each relation the same way, nested `select` included, or the
schema build throws. A `where` or `orderBy` function is the same only when it's the same function, so
share it. Load another version with `t.relation` or a field's `select`.

To filter a to-one relation, select it and return `null` from the resolver. Here a comment shows its
post's title only when the post is published:

```ts
builder.prismaObject('Comment', {
  fields: (t) => ({
    postTitle: t.string({
      nullable: true,
      select: { post: true },
      resolve: (comment) => (comment.post.published ? comment.post.title : null),
    }),
  }),
});
```

### Selecting per request

A field's `select` can also be a function of its arguments and context. Here only admins load the
email. A column that only some branches select is optional on the parent:

```ts
email: t.string({
  nullable: true,
  select: (_args, ctx) => (ctx.isAdmin ? { email: true } : {}),
  resolve: (user) => user.email ?? null,
}),
```

With `AsyncSelections: true` in the builder's types, the function can be async.

Its third argument, `nestedSelection`, loads a relation's rows for a field that returns them. See
[Indirect relations](./indirect-relations).

`select`, `query` and `where` callbacks run once when the plugin builds the query, not once per
row, so keep them free of side effects.

### Auth checks

Auth checks on the type, and other plugins' field options such as `authScopes` and `grantScopes`,
see:

- the primary key
- the columns and relations in the `select`s of the type and its interfaces
- on a `t.expose*` field, the exposed column

Only `resolve` can read what a field's own `select` loads. If a row is missing any of this, such as
a row of a variant model with its own table, the plugin reloads it by its key before the check.

## Return a type from Query and Mutation fields

Use `t.prismaField` for fields on `Query`, `Mutation`, or any other type that return your model
types. The plugin loads what the query selects in one statement.

To look up rows, pass a `query` with a `where`. It takes the same options as a relation's
[`query`](./relations#filtering-and-sorting): `where`, `orderBy`, `limit` and `offset`, or a
function of the field's arguments and context that returns them.

```ts
builder.queryType({
  fields: (t) => ({
    user: t.prismaField({
      type: 'User',
      nullable: true,
      args: { id: t.arg.id({ required: true }) },
      query: (args) => ({ where: { id: String(args.id) } }),
    }),
  }),
});
```

A single-row field returns the first row the query finds, and needs `collection`, `query` or
`resolve`. A list field without them loads every row:

```ts
builder.queryFields((t) => ({
  users: t.prismaField({ type: ['User'] }),
}));
```

### Paginating a list

For simple offset pagination, apply the field's arguments with `limit` and `offset`. Always include
an `orderBy` so pages are stable:

```ts
builder.queryFields((t) => ({
  posts: t.prismaField({
    type: ['Post'],
    args: { limit: t.arg.int(), offset: t.arg.int() },
    query: (args) => ({
      orderBy: { createdAt: 'desc' },
      limit: args.limit ?? 10,
      offset: args.offset ?? 0,
    }),
  }),
}));
```

For cursor-based pagination with page info and total counts, use `t.prismaConnection` instead. See
[Connections](./connections#paginate-a-query-field).

### Choosing the rows to start from

Rows load from the model's Collection, `orm.<Model>` from the plugin's `client`. To start from
other rows, such as through a fragment or a filter that needs the context, return a Collection from
`collection`. Don't call `.all()`, `.first()` or `.include()` on it; the plugin applies `query` and
what the query selects, then runs it.

```ts
builder.queryFields((t) => ({
  myPosts: t.prismaField({
    type: ['Post'],
    collection: (_root, _args, ctx) => ctx.db.orm.Post.where({ authorId: ctx.userId }),
    query: { orderBy: { createdAt: 'desc' } },
  }),
}));
```

### Mutations

To run the Collection yourself, such as for a write, pass `resolve` instead of `collection` and
`query`. It gets the model's Collection with what the query selects already added, and returns
what the Collection's methods return. Writes that return the row, such as `create`, `update`,
`upsert` and `delete`, then return everything the response needs without reading it again:

```ts
builder.mutationType({
  fields: (t) => ({
    renameUser: t.prismaField({
      type: 'User',
      nullable: true,
      args: {
        id: t.arg.id({ required: true }),
        firstName: t.arg.string({ required: true }),
      },
      resolve: (users, _root, args) =>
        users.where({ id: String(args.id) }).update({ firstName: args.firstName }),
    }),
  }),
});
```

For a [variant model](./interfaces#native-inheritance), the Collection is its base's narrowed to
it, such as `orm.Task.variant('bug')`. `update()` and `delete()` on it change the variant's first
row, so add a `where` for single-row writes. For a variant with its own table, `update` and
`delete` return only the base table's columns, so a response selecting the variant's own fields
fails. Write with `updateAndCount()` instead, then read the row with `first()`.

When the mutation returns a payload, build the write's Collection with `collectionFromInfo`, which
adds what the query selects, and pass the path to the row's field, such as `path: ['user']`. For an
interface or union, pass `typeName` to pick the type:

```ts
import { collectionFromInfo } from '@pothos/plugin-prisma-next';

const RenameUserPayload = builder
  .objectRef<{ user: typeof User.$inferType | null }>('RenameUserPayload')
  .implement({
    fields: (t) => ({ user: t.expose('user', { type: User, nullable: true }) }),
  });

builder.mutationField('renameUser', (t) =>
  t.field({
    type: RenameUserPayload,
    args: { id: t.arg.id({ required: true }), firstName: t.arg.string({ required: true }) },
    resolve: async (_root, args, ctx, info) => {
      const users = await collectionFromInfo({
        collection: ctx.db.orm.User.where({ id: String(args.id) }),
        context: ctx,
        info,
        path: ['user'],
      });
      return { user: await users.update({ firstName: args.firstName }) };
    },
  }),
);
```

See [Transactions](./setup#transactions) to run the write and the reads in one transaction.

Rows you load from a Collection that `resolve` or `collectionFromInfo` gives you belong to that
request. Don't share them with concurrent requests through a cache.

### `prismaFieldWithInput`

With the [with-input plugin](/docs/plugins/with-input), `t.prismaFieldWithInput` combines
`t.prismaField` with `t.fieldWithInput`, and takes `collection`, `query` or `resolve` the same way.
The `input` fields become an input object argument:

```ts
builder.mutationField('updateFirstName', (t) =>
  t.prismaFieldWithInput({
    type: 'User',
    nullable: true,
    input: {
      id: t.input.id({ required: true }),
      firstName: t.input.string({ required: true }),
    },
    resolve: (users, _root, args) =>
      users.where({ id: String(args.input.id) }).update({ firstName: args.input.firstName }),
  }),
);
```

## Adding fields

To add fields to a type from another file, use `prismaObjectField` or `prismaObjectFields`.
`builder.objectField` won't work here because it doesn't support `select`.

```ts
builder.prismaObjectField('User', 'displayName', (t) =>
  t.string({
    select: ['firstName', 'lastName'],
    resolve: (user) => `${user.firstName} ${user.lastName}`,
  }),
);
```

If the resolver reads the type's `select`, pass the ref that `prismaObject` returns instead of the
model name. Passing a variant's ref adds fields to that [variant](./variants).

```ts
const User = builder.prismaObject('User', {
  select: { firstName: true, lastName: true },
  fields: (t) => ({ id: t.exposeID('id') }),
});

builder.prismaObjectField(User, 'initials', (t) =>
  t.string({
    resolve: (user) => `${user.firstName[0]}${user.lastName[0]}`,
  }),
);
```
