## Defining types

`builder.prismaObject` takes a contract model name and the usual object type options. Column types
are inferred from the contract.

```ts
builder.prismaObject('User', {
  // Optional, defaults to the model name
  name: 'PostAuthor',
  fields: (t) => ({
    id: t.exposeID('id'),
    email: t.exposeString('email'),
  }),
});
```

This is the model's type, which a model name such as `type: 'User'` or `t.relation('author')`
refers to. `name` only renames it. A model has one such type: registering a second fails, so add
fields to it with `prismaObjectFields`, or define another type for the model with
[`variant`](./variants). That is a type variant, not a variant model of the contract, which
[native inheritance](./interfaces#native-inheritance) maps.

## Prisma fields

`t.prismaField` returns a contract-backed type. Its resolver returns an unexecuted Collection. The
plugin adds the selection for the query and runs it, with `.limit(1)` for single results.

```ts
builder.queryType({
  fields: (t) => ({
    me: t.prismaField({
      type: 'User',
      nullable: true,
      resolve: (_root, _args, ctx) => ctx.db.orm.User.where((user) => user.id.eq(ctx.userId)),
    }),
  }),
});
```

Return the Collection without calling `.all()` or `.first()`. The types reject materialized
rows, because the plugin can't add the selection to them, and the plugin rejects a Collection with
an `.include()`, because it includes what the query selects itself. Filter a relation with its field's
[`query`](./relations#filtering-and-sorting) instead. A nullable field resolves to `null` when the
Collection is empty.

### Mutations

Perform the write, then return a Collection for the result:

```ts
builder.mutationType({
  fields: (t) => ({
    renameUser: t.prismaField({
      type: 'User',
      args: {
        id: t.arg.id({ required: true }),
        firstName: t.arg.string({ required: true }),
      },
      resolve: async (_root, args, ctx) => {
        const user = ctx.db.orm.User.where({ id: String(args.id) });
        await user.update({ firstName: args.firstName });
        return user;
      },
    }),
  }),
});
```

To run the write and the reads in one transaction, see [Transactions](./setup#transactions).

### Payloads and other resolvers

A mutation payload can hold what identifies the result and give it a `t.prismaField`, which
returns a Collection like a root field does. The result then loads after the write, in one more
statement:

```ts
const RenameUserPayload = builder.objectRef<{ userId: string }>('RenameUserPayload').implement({
  fields: (t) => ({
    user: t.prismaField({
      type: 'User',
      resolve: (payload, _args, ctx) => ctx.db.orm.User.where({ id: payload.userId }),
    }),
  }),
});
```

A field that isn't a `prismaField`, such as a mutation returning a payload, can apply its selection
with `collectionFromInfo`. `path` leads to the rows' field in the payload. The rows that the
collection's reads and writes return load what the query selects, relations included, so the
payload's fields don't load again. This works for a write that returns the row, such as `update`
or `delete`:

```ts
import { collectionFromInfo } from '@pothos/plugin-prisma-next';

const RenameUserPayload = builder
  .objectRef<{ user: typeof User.$inferType | null }>('RenameUserPayload')
  .implement({
    fields: (t) => ({ user: t.field({ type: User, nullable: true, resolve: (p) => p.user }) }),
  });

builder.mutationField('renameUser', (t) =>
  t.field({
    type: RenameUserPayload,
    args: { id: t.arg.id({ required: true }), firstName: t.arg.string({ required: true }) },
    resolve: async (_root, args, ctx, info) => {
      const users = await collectionFromInfo({
        collection: ctx.db.orm.User.where({ id: String(args.id) }),
        context: ctx,
        info,
        path: ['user'],
      });
      return { user: await users.update({ firstName: args.firstName }) };
    },
  }),
);
```

`typeName` names the type the rows resolve as when the path leads to an interface or union.

### Subscriptions

In a subscription field, `resolve` receives each value `subscribe` yields and returns a Collection
to load it from:

```ts
builder.subscriptionType({
  fields: (t) => ({
    userChanged: t.prismaField({
      type: 'User',
      nullable: true,
      subscribe: (_root, _args, ctx) => ctx.pubsub.subscribe('userChanged'),
      resolve: (id, _args, ctx) => ctx.db.orm.User.where({ id }),
    }),
  }),
});
```

### With input

With the [with-input plugin](../with-input), `t.prismaFieldWithInput` works the same way:

```ts
builder.queryFields((t) => ({
  userByEmail: t.prismaFieldWithInput({
    type: 'User',
    nullable: true,
    input: { email: t.input.string({ required: true }) },
    resolve: (_root, args, ctx) =>
      ctx.db.orm.User.where((user) => user.email.eq(args.input.email)),
  }),
}));
```

## Selections

`select` on the type loads columns whenever the type is queried. `select` on a field loads them
when the field is queried. A resolver's parent only includes what was selected, plus the model's
primary key, which is always loaded.

```ts
builder.prismaObject('User', {
  select: { firstName: true, lastName: true },
  fields: (t) => ({
    fullName: t.string({
      resolve: (user) => `${user.firstName} ${user.lastName}`,
    }),
    initials: t.string({
      select: ['firstName', 'lastName'],
      resolve: (user) => `${user.firstName[0]}${user.lastName[0]}`,
    }),
    publishedPostCount: t.field({
      type: 'Int',
      select: {
        posts: (posts) => ({ publishedCount: posts.where({ published: 1 }).count() }),
      },
      resolve: (user) => user.publishedCount,
    }),
  }),
});
```

A `select` accepts:

- `{ column: true }` or `['column']`: a column.
- `{ relation: true }`: the related rows.
- `{ relation: { where, orderBy, limit, offset } }`: filtered or sorted related rows. A to-one
  relation takes only `where`, and only on a field's `select`.
- `{ relation: (collection) => ({ ... }) }`: counts, aggregates, or other values computed from a
  to-many relation. Each key is added to the parent, so it can't name a column or relation of the
  model, or a key another relation of the `select` computes.

`t.expose*` only works on model columns. Read a computed key with a resolver, such as
`t.int({ resolve: (user) => user.postCount })`.

The function form only works on to-many relations. To filter a to-one relation, use the object form
on a field:

```ts
authorName: t.string({
  nullable: true,
  select: { author: { where: { firstName: 'Alice' } } },
  resolve: (post) => post.author?.firstName ?? null,
}),
```

A filtered to-one relation can be `null` even when its foreign key is required.

The `select` of a type takes only `true` for a to-one relation. The ORM includes a to-one relation
once per row, and every reader of the row shares a type's `select`. A field with a filter loads its
own version of the relation, reloading the row when the rest of the query needs the unfiltered one.

A field returning the type must return the key plus the columns and to-one relations of the type's
`select`, so type-level checks such as `authScopes` see them. To-many relations and computed values
in a type's `select`, and fields' own `select`s, load per field, so a type-level check shouldn't
rely on them unless the row came from a prisma field, relation or connection. A field's own
`select` may be missing under `@defer` until the field resolves.

A field's `select` can also be a function of the field's arguments and context returning the
object form. A column array is a static `select` only. With `AsyncSelections: true` in the
builder's types, the function can be async. Columns that only some of its branches select are
optional on the parent, as are the columns of a static array variable, such as
`select: someColumns`:

```ts
email: t.string({
  nullable: true,
  select: (_args, ctx) => (ctx.isAdmin ? { email: true, firstName: true } : { firstName: true }),
  resolve: (user) => user.email ?? null,
}),
```

## Adding fields

`builder.objectField` and `builder.objectFields` don't support `select`. Use
`prismaObjectField` or `prismaObjectFields` instead:

```ts
builder.prismaObjectField('User', 'displayName', (t) =>
  t.string({
    select: ['firstName', 'lastName'],
    resolve: (user) => `${user.firstName} ${user.lastName}`,
  }),
);
```

With a model name, the parent only includes the field's own `select`. Pass the ref returned by
`prismaObject` to use the type's selections, or to extend a [variant](./variants):

```ts
const User = builder.prismaObject('User', {
  select: ['firstName'],
  fields: (t) => ({ id: t.exposeID('id') }),
});

builder.prismaObjectField(User, 'displayName', (t) =>
  t.string({
    select: ['lastName'],
    resolve: (user) => `${user.firstName} ${user.lastName}`,
  }),
);
```
