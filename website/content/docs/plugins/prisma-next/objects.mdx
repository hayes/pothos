## Defining types

`builder.prismaObject` takes a contract model name and the usual object type options. Column types
are inferred from the contract.

```ts
builder.prismaObject('User', {
  // Optional, defaults to the model name
  name: 'PostAuthor',
  fields: (t) => ({
    id: t.exposeID('id'),
    email: t.exposeString('email'),
  }),
});
```

Each model has one `prismaObject`. To add fields to it elsewhere, use
[`prismaObjectFields`](#adding-fields). To expose the same model as another GraphQL type, define a
[`variant`](./variants).

## Selections

A `select` on the type is loaded whenever the type is queried. A `select` on a field is loaded only
when that field is queried. The primary key is always loaded.

```ts
builder.prismaObject('User', {
  select: { firstName: true, lastName: true },
  fields: (t) => ({
    fullName: t.string({
      resolve: (user) => `${user.firstName} ${user.lastName}`,
    }),
    initials: t.string({
      select: ['firstName', 'lastName'],
      resolve: (user) => `${user.firstName[0]}${user.lastName[0]}`,
    }),
    publishedPostCount: t.field({
      type: 'Int',
      select: {
        posts: (posts) => ({ publishedCount: posts.where({ published: 1 }).count() }),
      },
      resolve: (user) => user.publishedCount,
    }),
  }),
});
```

A `select` accepts:

- Columns: `{ email: true }` or `['email']`.
- Relations: `{ posts: true }`.
- Filtered or sorted relations: `{ posts: { where: { published: 1 }, orderBy: (post) => post.createdAt.desc(), limit: 5 } }`.
  A to-one relation takes only `where`, and only in a field's `select`.
- Counts and aggregates of a to-many relation:
  `{ posts: (posts) => ({ postCount: posts.count() }) }`. Each key (`postCount`) is added to the
  row, so it can't reuse a column or relation name.

Read computed keys with a resolver; `t.expose*` only works on columns.

To filter a to-one relation, use the object form in a field's `select`. The result can be `null`
even when the foreign key is required:

```ts
authorName: t.string({
  nullable: true,
  select: { author: { where: { firstName: 'Alice' } } },
  resolve: (post) => post.author?.firstName ?? null,
}),
```

A field's `select` can also be a function of its arguments and context. With `AsyncSelections: true`
in the builder's types, it can be async. A column that only some branches select is optional on the
parent:

```ts
email: t.string({
  nullable: true,
  select: (_args, ctx) => (ctx.isAdmin ? { email: true, firstName: true } : { firstName: true }),
  resolve: (user) => user.email ?? null,
}),
```

`select`, `query`, `where` and `orderBy` callbacks run once per planned query, not per row, so keep
them free of side effects.

Type-level checks such as `authScopes` always see the primary key and the columns and to-one
relations in the type's `select`. Other data may not be loaded yet, unless the row came from a
prisma field, relation or connection.

## Prisma fields

A `t.prismaField` resolver returns a Collection without running it. The plugin adds what the query
selects, then runs it.

```ts
builder.queryType({
  fields: (t) => ({
    me: t.prismaField({
      type: 'User',
      nullable: true,
      resolve: (_root, _args, ctx) => ctx.db.orm.User.where((user) => user.id.eq(ctx.userId)),
    }),
  }),
});
```

Don't call `.all()`, `.first()` or `.include()` on the Collection. To filter a relation, use its
field's [`query`](./relations#filtering-and-sorting).

### Mutations

Run the write, then return a Collection that finds the updated row by its ID:

```ts
builder.mutationType({
  fields: (t) => ({
    renameUser: t.prismaField({
      type: 'User',
      nullable: true,
      args: {
        id: t.arg.id({ required: true }),
        firstName: t.arg.string({ required: true }),
      },
      resolve: async (_root, args, ctx) => {
        const user = await ctx.db.orm.User.where({ id: String(args.id) }).update({
          firstName: args.firstName,
        });
        return user && ctx.db.orm.User.where({ id: user.id });
      },
    }),
  }),
});
```

See [Transactions](./setup#transactions) to run the write and the reads in one transaction.

To load the result in the write itself, use `collectionFromInfo`. Writes that return the row, such
as `update`, then return what the query selects. Pass `path: ['user']` when the resolver returns a
payload containing a `user` field. For an interface or union, pass `typeName` to pick the type:

```ts
import { collectionFromInfo } from '@pothos/plugin-prisma-next';

const RenameUserPayload = builder.objectRef<{ user: unknown }>('RenameUserPayload').implement({
  fields: (t) => ({ user: t.field({ type: User, nullable: true, resolve: (p) => p.user as never }) }),
});

builder.mutationField('renameUser', (t) =>
  t.field({
    type: RenameUserPayload,
    args: { id: t.arg.id({ required: true }), firstName: t.arg.string({ required: true }) },
    resolve: async (_root, args, ctx, info) => {
      const users = await collectionFromInfo({
        collection: ctx.db.orm.User.where({ id: String(args.id) }),
        context: ctx,
        info,
        path: ['user'],
      });
      return { user: await users.update({ firstName: args.firstName }) };
    },
  }),
);
```

## Adding fields

`builder.objectField` doesn't support `select`. Use `prismaObjectField` or `prismaObjectFields`
instead:

```ts
builder.prismaObjectField('User', 'displayName', (t) =>
  t.string({
    select: ['firstName', 'lastName'],
    resolve: (user) => `${user.firstName} ${user.lastName}`,
  }),
);
```

If the resolver reads the type's `select`, pass the ref that `prismaObject` returns instead of the
model name. A variant's ref adds fields to that [variant](./variants).

```ts
const User = builder.prismaObject('User', {
  select: ['firstName'],
  fields: (t) => ({ id: t.exposeID('id') }),
});

builder.prismaObjectField(User, 'displayName', (t) =>
  t.string({
    select: ['lastName'],
    resolve: (user) => `${user.firstName} ${user.lastName}`,
  }),
);
```
