title: Connections
description: Relay connections backed by Prisma Collections

Connections add cursor pagination to a list. They require the [Relay plugin](../relay). Use
`t.prismaConnection` to paginate a Collection your resolver returns, and `t.relatedConnection` to
paginate a relation.

## Paginate a query field

```ts
builder.queryFields((t) => ({
  posts: t.prismaConnection({
    type: 'Post',
    orderBy: { createdAt: 'desc' },
    totalCount: true,
    resolve: (_root, _args, ctx) => ctx.db.orm.Post.where({ published: 1 }),
  }),
}));
```

Return the Collection without ordering, paging or `include()`. The plugin orders it, pages it, and
adds what the query selects. `t.prismaConnection` takes:

- `orderBy`: the columns to order by, or `(args, ctx) => orderBy`. Defaults to the primary key. See
  [Ordering and cursors](#ordering-and-cursors).
- `defaultSize` / `maxSize`: page sizes, or `(args, ctx) => number`. Default to the plugin's
  [connection size options](./setup#plugin-options).
- `totalCount`: `true` counts the Collection, or pass `(parent, args, ctx, info) => number`. The
  count only runs when `totalCount` is selected.
- `args`: extra arguments for filtering or sorting.

Connection and edge types can be customized as with the [Relay plugin](../relay).

## Paginate a relation

To paginate a relation, such as a user's posts, use `t.relatedConnection`:

<include cwd lang="typescript" meta='playground example="plugin-prisma-next" query="{ users { fullName postConnection(first: 1) { totalCount edges { node { title } } pageInfo { endCursor hasNextPage } } } }"'>playground-examples/plugin-prisma-next/types/user.ts#user-post-connection</include>

It takes the same options as `t.prismaConnection`, and filters with `query`: `{ where }` or
`(args, ctx) => ({ where })`. `totalCount` counts the rows matching `query.where`, unless
[`filterConnectionTotalCount`](./setup#plugin-options) is `false`.

Index the foreign key together with the order columns.

## Ordering and cursors

`orderBy` on either kind of connection takes columns of the model, each with a direction. You can't
order by relation columns, aggregates or expressions. Nullable columns sort nulls last unless you set
`nulls`:

```ts
orderBy: { score: { direction: 'desc', nulls: 'first' } },
```

If the order doesn't include a unique key:

- The plugin adds the primary key to the end, in the same direction as the last column.
- If the primary key can't be ordered, it uses the first non-null unique key that can.

On PostgreSQL, index the order columns with matching null placement. For `{ score: 'desc' }`, that's
`CREATE INDEX ON post (score DESC NULLS LAST, id DESC)`.

To let clients choose the order, pass a function of the arguments:

<include cwd lang="typescript" meta='playground example="plugin-prisma-next" query="{ posts(first: 2, newestFirst: true) { totalCount edges { node { title } } pageInfo { endCursor hasNextPage } } }"'>playground-examples/plugin-prisma-next/queries.ts#posts-query</include>

Cursors contain the values of the order columns, readable by clients, so don't order by columns
clients shouldn't see.

- Columns the ORM can't order, such as bytes, can't be in the order.
- A timestamp read as a JavaScript `Date` keeps only milliseconds, so you can't order by one with a
  precision above 3. Bare `DateTime` is fine; on PostgreSQL, use `TimestamptzTemporal` for finer
  timestamps.

An `orderBy` object that breaks these rules fails the schema build. An `orderBy` function fails
each request that returns such an order.

## Custom connections

When the nodes aren't a relation of the parent, such as the users who commented on a post, define
the connection yourself with `t.connection` and page it with `prismaConnectionHelpers`. The helper
takes a model name or a prisma type ref, and `orderBy`, `defaultSize`, `maxSize`, `args` and
`query` as `t.relatedConnection` does. Its `totalCount` takes `true`, but not a function. For a
custom count, see below.

### Paginate through a join model

Here each row is a `Comment`, and each node is that comment's author. `select` lists what each
comment loads, and `nodeSelection()` marks `author` as the relation that holds the node.
`resolveNode` returns the node for each comment:

```ts
import { prismaConnectionHelpers } from '@pothos/plugin-prisma-next';

const commenters = prismaConnectionHelpers(builder, 'Comment', {
  orderBy: { createdAt: 'desc' },
  totalCount: true,
  select: (nodeSelection) => ({ author: nodeSelection() }),
  resolveNode: (comment) => comment.author,
});

builder.prismaObjectField('Post', 'commenters', (t) =>
  t.connection(
    {
      type: User,
      select: { comments: commenters.page },
      resolve: (post, args, ctx) => commenters.resolve(post.comments, args, ctx, post),
    },
    commenters.connectionOptions({}),
  ),
);
```

`commenters.page` loads one page of comments with the post, and `commenters.resolve` builds the
connection from them.

### Paginate a Collection you load yourself

To run the query in your own resolver, use `applyPagination`. Here a root field pages through the
authors of all comments:

```ts
builder.queryFields((t) => ({
  recentCommenters: t.connection(
    {
      type: User,
      resolve: async (_root, args, ctx, info) => {
        const { collection, totalCountPromise, wrap } = await commenters.applyPagination(
          ctx.db.orm.Comment,
          args,
          ctx,
          info,
        );
        return wrap(await collection.all(), await totalCountPromise);
      },
    },
    commenters.connectionOptions({}),
  ),
}));
```

With `info`, each row loads what the query selects. Without it, rows load every column.
`totalCountPromise` is `undefined` when `totalCount` isn't selected.

`connectionOptions` adds the `totalCount` field. For a custom count, leave `totalCount` unset, add
the field yourself, and pass the count to `wrap(rows, count)`.
