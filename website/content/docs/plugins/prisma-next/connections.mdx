title: Connections
description: Relay connections backed by Prisma Collections

Connections require the [Relay plugin](../relay). Use `t.prismaConnection` for a Collection your
resolver returns, and `t.relatedConnection` for a relation.

## prismaConnection

```ts
builder.queryFields((t) => ({
  posts: t.prismaConnection({
    type: 'Post',
    orderBy: { createdAt: 'desc' },
    totalCount: true,
    resolve: (_root, _args, ctx) => ctx.db.orm.Post.where({ published: 1 }),
  }),
}));
```

Return a Collection without ordering, paging or `include()`. The plugin orders it, pages it, and
adds what the query selects.

- `orderBy`: the columns to order by, or `(args, ctx) => orderBy`. Defaults to the primary key. See
  [Ordering and cursors](#ordering-and-cursors).
- `defaultSize` / `maxSize`: page sizes, or `(args, ctx) => number`. Default to the plugin's
  [connection size options](./setup#plugin-options).
- `totalCount`: `true` counts the Collection, or pass `(parent, args, ctx, info) => number`. The
  count only runs when `totalCount` is selected.
- `args`: extra arguments for filtering or sorting.

Connection and edge types can be customized as with the [Relay plugin](../relay).

## Ordering and cursors

`orderBy` takes columns of the model, each with a direction. You can't order by relation columns,
aggregates or expressions. Nullable columns sort nulls last unless you set `nulls`:

```ts
orderBy: { score: { direction: 'desc', nulls: 'first' } },
```

The plugin adds the primary key (or the first non-null unique key) to the end of the order, so pages
are stable. On
PostgreSQL, index the order columns with matching null placement, such as
`CREATE INDEX ON post (score DESC NULLS LAST, id DESC)` for `{ score: 'desc' }`.

The function form chooses the order per request:

<include cwd lang="typescript" meta='playground example="plugin-prisma-next" query="{ posts(first: 2, newestFirst: true) { totalCount edges { node { title } } pageInfo { endCursor hasNextPage } } }"'>playground-examples/plugin-prisma-next/queries.ts#posts-query</include>

A cursor holds the values of the order columns in base64, so clients can read them. Don't order by
columns clients shouldn't see. A cursor only works with the order it came from, and fails with
`Invalid cursor` otherwise.

- Bytes columns can't be ordered.
- On PostgreSQL, a timestamp read as a JavaScript `Date` keeps only milliseconds, so ordering by
  one with a precision above 3 is a schema build error. Bare `DateTime` is fine; use
  `TimestamptzTemporal` for finer timestamps.

## relatedConnection

<include cwd lang="typescript" meta='playground example="plugin-prisma-next" query="{ users { fullName postConnection(first: 1) { totalCount edges { node { title } } pageInfo { endCursor hasNextPage } } } }"'>playground-examples/plugin-prisma-next/types/user.ts#user-post-connection</include>

The page loads with the parent query. It takes the same options as `t.prismaConnection`, and
filters with `query`: `{ where }` or `(args, ctx) => ({ where })`. `totalCount` counts the rows
matching `query.where`, unless
[`filterConnectionTotalCount`](./setup#plugin-options) is `false`.

The database pages each parent's rows separately, so index the foreign key together with the order
columns.

## Connection helpers

`prismaConnectionHelpers` pages a connection you define yourself with `t.connection`. Use it when
the nodes aren't a relation of the parent, such as the users who commented on a post. It takes a
model name or a prisma type ref, and the options of `t.relatedConnection`.

### Through a join model

Here each row is a `Comment`. `select` lists what each comment loads, and `nodeSelection()` marks
`author` as the relation that holds the node. `resolveNode` returns the node for each comment:

```ts
import { prismaConnectionHelpers } from '@pothos/plugin-prisma-next';

const commenters = prismaConnectionHelpers(builder, 'Comment', {
  orderBy: { createdAt: 'desc' },
  totalCount: true,
  select: (nodeSelection) => ({ body: true, author: nodeSelection() }),
  resolveNode: (comment) => comment.author,
});

builder.prismaObjectField('Post', 'commenters', (t) =>
  t.connection(
    {
      type: User,
      select: { comments: commenters.page },
      resolve: (post, args, ctx) => commenters.resolve(post.comments, args, ctx, post),
    },
    commenters.connectionOptions({}),
  ),
);
```

`commenters.page` loads one page of comments, and their count, with the post. Pass
`commenters.resolve` the post the resolver received, not a copy, because the count is stored on it.

### Paging a collection

`applyPagination` pages a Collection the resolver loads itself:

```ts
builder.queryFields((t) => ({
  commenters: t.connection(
    {
      type: User,
      resolve: async (_root, args, ctx, info) => {
        const { collection, totalCountPromise, wrap } = await commenters.applyPagination(
          ctx.db.orm.Comment,
          args,
          ctx,
          info,
        );
        return wrap(await collection.all(), await totalCountPromise);
      },
    },
    commenters.connectionOptions({}),
  ),
}));
```

With `info`, each row loads what the query selects. Without it, rows load every column.
`totalCountPromise` is `undefined` when `totalCount` isn't selected.

`connectionOptions` adds the `totalCount` field. For a custom count, leave `totalCount` unset, add
the field yourself, and pass the count to `wrap(rows, count)`.
