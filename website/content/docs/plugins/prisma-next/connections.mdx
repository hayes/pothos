Connections add cursor pagination to a list. They require the [Relay plugin](../relay). Use
`t.prismaConnection` to paginate a model's rows, and `t.relatedConnection` to paginate a relation.

## Paginate a query field

```ts
builder.queryFields((t) => ({
  posts: t.prismaConnection({
    type: 'Post',
    query: { where: { published: 1 }, orderBy: { createdAt: 'desc' } },
    totalCount: true,
  }),
}));
```

The plugin orders the model's Collection by `query.orderBy` and the cursor, pages it, and adds what
the query selects. `t.prismaConnection` takes:

- `collection`: `(parent, args, ctx, info) => Collection`, the rows to page instead of the model's,
  such as `ctx.db.orm.Post.where({ authorId: ctx.userId })`. Return it without `orderBy()` or
  `include()`. `limit()`, `offset()` and `distinct()` aren't supported.
- `query`: `{ where, orderBy }`, or `(args, ctx) => ({ where, orderBy })`. `where` filters the
  Collection, and `orderBy` orders it, by the primary key when omitted. See
  [Ordering and cursors](#ordering-and-cursors).
- `defaultSize` / `maxSize`: page sizes, or `(args, ctx) => number`. Default to the plugin's
  [connection size options](./setup#plugin-options).
- `totalCount`: `true` counts the rows, filtered by `query.where`, or pass
  `(parent, args, ctx, info) => number`. The count only runs when `totalCount` is selected.
- `args`: extra arguments for filtering or sorting.

Connection and edge types can be customized as with the [Relay plugin](../relay), including
`edgesNullable` and `nodeNullable`.

### Before or after loading

`t.prismaConnection` loads the page itself. To run code before or after the load, such as a check or
a side effect, build the connection with `t.connection` and
[connection helpers](#custom-connections):

```ts
import { prismaConnectionHelpers } from '@pothos/plugin-prisma-next';

const userPage = prismaConnectionHelpers(builder, 'User', {
  query: { orderBy: { id: 'asc' } },
  totalCount: true,
});

builder.queryField('users', (t) =>
  t.connection({
    type: User,
    args: userPage.getArgs(),
    resolve: async (_root, args, ctx, info) => {
      if (!ctx.isAdmin) {
        throw new Error('Not allowed.');
      }
      const rows = await userPage.load(ctx.db.orm.User, args, ctx, info);
      // Read or change the rows here.
      return userPage.resolve(rows, args, ctx);
    },
  }),
);
```

`load` loads the page as `t.prismaConnection` does, with one row past it to set `hasNextPage`. Pass
`resolve` the list `load` returned, or it doesn't set `totalCount`.

## Paginate a relation

To paginate a relation, such as a user's posts, use `t.relatedConnection`:

It takes the same options as `t.prismaConnection` except `collection`. `totalCount` counts the rows
matching `query.where`, unless [`filterConnectionTotalCount`](./setup#plugin-options) is `false`.

Index the foreign key together with the order columns.

## Ordering and cursors

A connection's `query.orderBy` takes columns of the model, each with a direction, as a
[relation's](./relations#filtering-and-sorting) does. You can't order a connection by relation
columns, aggregates or expressions. Nullable columns sort nulls last unless you set `nulls`:

```ts
query: { orderBy: { score: { direction: 'desc', nulls: 'first' } } },
```

If the order doesn't include a unique key:

- The plugin adds the primary key to the end, in the same direction as the last column.
- If the primary key can't be ordered, it uses the first non-null unique key that can.

On PostgreSQL, index the order columns with matching null placement. For `{ score: 'desc' }`, that's
`CREATE INDEX ON post (score DESC NULLS LAST, id DESC)`.

To let clients choose the order, pass a function of the arguments:

<include cwd lang="typescript" meta='playground example="plugin-prisma-next" query="{ posts(first: 2, newestFirst: true) { totalCount edges { node { title } } pageInfo { endCursor hasNextPage } } }"'>playground-examples/plugin-prisma-next/queries.ts#posts-query</include>

Cursors contain the values of the order columns, readable by clients, so don't order by columns
clients shouldn't see.

- Columns the ORM can't order, such as bytes, can't be in the order.
- A timestamp read as a JavaScript `Date` keeps only milliseconds, so you can't order by one with a
  precision above 3. Bare `DateTime` is fine; on PostgreSQL, use `TimestamptzTemporal` for finer
  timestamps.

A `query` object whose `orderBy` breaks these rules fails the schema build. A `query` function
fails each request that returns such an order.

## Custom connections

When the nodes aren't a relation of the parent, such as the users who commented on a post, define
the connection yourself with `t.connection` and page it with `prismaConnectionHelpers`. The helper
takes a model name or a prisma type ref, and `query`, `defaultSize`, `maxSize`, `totalCount` and
`args` as `t.relatedConnection` does. `totalCount` takes `true`, but not a function.

Here each row is a `Comment`, and each node is that comment's author. `select` lists what each
comment loads, and `nodeSelection()` marks `author` as the relation that holds the node.
`resolveNode` returns the node for each comment:

```ts
import { prismaConnectionHelpers } from '@pothos/plugin-prisma-next';

const commenters = prismaConnectionHelpers(builder, 'Comment', {
  query: { orderBy: { createdAt: 'desc' } },
  totalCount: true,
  select: (nodeSelection) => ({ createdAt: true, author: nodeSelection() }),
  resolveNode: (comment) => comment.author,
});

builder.prismaObjectField('Post', 'commenters', (t) =>
  t.connection(
    {
      type: User,
      select: (args, ctx, nestedSelection) => ({
        comments: commenters.getQuery(args, ctx, nestedSelection),
      }),
      resolve: (post, args, ctx) => commenters.resolve(post.comments, args, ctx),
    },
    {
      fields: (connection) => ({
        totalCount: connection.int({ resolve: (page) => page.totalCount }),
      }),
    },
  ),
);
```

`getQuery` loads one page of comments with the post, and its count when the connection selects a
field named `totalCount`. `resolve` pages any list of rows by the field's arguments, as `getQuery`
does. `totalCount` is set when the rows are the list `getQuery` or `load` loaded, or when you pass
a count. Without `resolveNode`, the rows are the nodes.

To count the rows yourself, such as on MySQL, where Prisma can't count them yet, pass the count to
`resolve`: `commenters.resolve(rows, args, ctx, { totalCount })`.

Put `getQuery` at the top level of a field's `select`, not inside another relation's entry. When
the connection is beneath that field, such as on a wrapper type the field returns, prefix the path
`getQuery` passes to `nestedSelection`:

```ts
const PostActivity = builder
  .objectRef<{ comments: Parameters<typeof commenters.resolve>[0] }>('PostActivity')
  .implement({
    fields: (t) => ({
      commenters: t.connection({
        type: User,
        args: commenters.getArgs(),
        resolve: (activity, args, ctx) => commenters.resolve(activity.comments, args, ctx),
      }),
    }),
  });

builder.prismaObjectField('Post', 'activity', (t) =>
  t.field({
    type: PostActivity,
    select: (args, ctx, nestedSelection) => ({
      comments: commenters.getQuery(args, ctx, ({ path }) =>
        nestedSelection({ path: ['commenters', ...path] }),
      ),
    }),
    resolve: (post) => ({ comments: post.comments }),
  }),
);
```

The page follows the arguments of the connection field, `commenters`, not those of `activity`.
Aliases of `commenters` beneath one `activity` must pass the same arguments, or the root field fails.

`select` and `query` also receive the connection's arguments and context. Add the helper's `args`
to the connection field with `args: commenters.getArgs()`.

### Root fields

On a root field, `load` pages a collection of the helper's model. It loads the page with the
nodes' selection in one statement, and the count when `totalCount` is selected. As with
`t.prismaConnection`, the collection can't use `include()` or `orderBy()`. Pass the rows to
`resolve`. With `resolveNode`, each edge also holds its row, so edge fields can read it:

```ts
builder.queryField('postCommenters', (t) =>
  t.connection(
    {
      type: User,
      args: { ...commenters.getArgs(), postId: t.arg.id({ required: true }) },
      resolve: async (_root, args, ctx, info) => {
        const comments = ctx.db.orm.Comment.where({ postId: String(args.postId) });
        const rows = await commenters.load(comments, args, ctx, info);
        return commenters.resolve(rows, args, ctx);
      },
    },
    {},
    {
      fields: (edge) => ({
        commentedAt: edge.string({ resolve: (comment) => comment.createdAt.toISOString() }),
      }),
    },
  ),
);
```
