title: Interfaces
description: GraphQL interfaces backed by contract models
---

`builder.prismaInterface` takes the same options as `builder.prismaObject` and creates an
interface. Objects implementing it must use the same model, or one of its
[variant models](#native-inheritance):

```ts
const Person = builder.prismaInterface('User', {
  variant: 'Person',
  select: ['email'],
  resolveType: (user) => (user.email.endsWith('@admin.example.com') ? 'Admin' : 'User'),
  fields: (t) => ({
    id: t.exposeID('id'),
    firstName: t.exposeString('firstName'),
  }),
});

builder.prismaObject('User', {
  interfaces: [Person],
  fields: (t) => ({
    email: t.exposeString('email'),
  }),
});
```

`t.prismaField` and `t.prismaConnection` take an interface ref as `type`, and so do `t.relation`
and `t.relatedConnection`. A relation also returns an interface when its target model is registered
with `prismaInterface`, as in [Native inheritance](#native-inheritance).

Objects don't take `isTypeOf`. Give the interface a `resolveType` to pick each row's type, and
list the columns it reads in the interface's `select`. An interface of a model with variants
resolves rows by its discriminator without one, as in [Native inheritance](#native-inheritance):

```ts
builder.prismaObject('User', {
  variant: 'Admin',
  interfaces: [Person],
  fields: (t) => ({
    email: t.exposeString('email'),
  }),
});

builder.queryFields((t) => ({
  people: t.prismaField({
    type: [Person],
    resolve: (_root, _args, ctx) => ctx.db.orm.User,
  }),
}));
```

To return a row through `Node` or an interface from `builder.interfaceRef()`, brand it with the
type's `addBrand`, such as `User.addBrand(row)`, which requires the key plus the type's `select`.
Unbranded, it fails with `Abstract type ... must resolve`. A row with a `__typename`, or a
hand-written `resolveType` on such an interface, skips that check like a cast, so the row may lack
the type's `select`.

A plain row returned for a `prismaInterface` is only typed to hold the interface's `select` plus the
discriminator. An implementation's own `select`, such as `Bug`'s `severity`, loads per field, so for
type-level checks that read it, return the row from a prisma field or brand it with that type's
`addBrand`, which requires its `select`.

Add fields with `prismaInterfaceField` or `prismaInterfaceFields`, passing the ref:

```ts
builder.prismaInterfaceField(Person, 'displayName', (t) =>
  t.string({
    select: ['firstName', 'lastName'],
    resolve: (person) => `${person.firstName} ${person.lastName}`,
  }),
);
```

Interfaces accept `variant` like objects do, for a [type variant](./variants) of the interface.

## Selections

An object's fields can read its interfaces' `select`. A row loaded through the interface also
loads each implementation's `select`, so type-level `authScopes` can read it without a
`... on Type` fragment.

A type's `select` takes only `true` for a to-one relation.

## Native inheritance

A base model with variants in the contract maps to an interface, with an object for each variant.
The interface selects the discriminator and resolves each row to its variant's type:

```ts
const task = builder.prismaInterface('Task', {
  fields: (t) => ({
    id: t.exposeID('id'),
    owner: t.relation('owner'),
  }),
});

builder.prismaObject('Bug', {
  interfaces: [task],
  fields: (t) => ({
    severity: t.exposeString('severity'),
  }),
});

builder.queryType({
  fields: (t) => ({
    tasks: t.prismaField({
      type: [task],
      resolve: (_root, _args, ctx) => ctx.db.orm.Task,
    }),
    bugs: t.prismaField({
      type: ['Bug'],
      resolve: (_root, _args, ctx) => ctx.db.orm.Task.variant('bug'),
    }),
  }),
});
```

- Return a variant type from `orm.Base.variant(value)`. Prisma doesn't filter `orm.Bug` by the
  discriminator, so its type is rejected.
- A relation declared on a variant loads only from a collection narrowed to it. A variant type's
  `select` can't name one, and is rejected when the schema is built. Put it in a field's `select`,
  or use a relation field.
- Each variant needs exactly one implementing type, unless the interface has a `resolveType`.
- A relation name declared by several variants can't be loaded, because a level of the query holds
  one relation of a name. A field or `select` that names it fails when the schema is built. The
  rest of the hierarchy works.
- `prismaNode` works on a variant, and loads it through `orm.Task.variant('bug')`. A `collection`
  option is used as given, so it returns the narrowed collection itself.
- With `type` set to the ref of a variant model's object, such as `Bug`, `t.relation` and
  `t.relatedConnection` return and count only that variant's rows. A to-one relation with such a
  `type` is nullable.
