---
title: Interfaces
description: GraphQL interfaces backed by contract models
---

`builder.prismaInterface` takes the same options as `builder.prismaObject` and creates an
interface. Objects implementing it must use the same model:

```ts
const Person = builder.prismaInterface('User', {
  name: 'Person',
  fields: (t) => ({
    id: t.exposeID('id'),
    firstName: t.exposeString('firstName'),
  }),
});

builder.prismaObject('User', {
  interfaces: [Person],
  isTypeOf: () => true,
  fields: (t) => ({
    email: t.exposeString('email'),
  }),
});
```

`t.prismaField`, `t.prismaConnection`, and `t.relation` can return an interface. Give the
implementations an `isTypeOf`, or the interface a `resolveType`. List the columns an `isTypeOf`
reads in that object's `select`, and the columns a `resolveType` reads in the interface's `select`:

```ts
builder.prismaObject('User', {
  variant: 'Admin',
  interfaces: [Person],
  select: ['email'],
  isTypeOf: (user) => user.email.endsWith('@admin.example.com'),
  fields: (t) => ({
    email: t.exposeString('email'),
  }),
});

builder.queryFields((t) => ({
  people: t.prismaField({
    type: [Person],
    resolve: (_root, _args, ctx) => ctx.db.orm.User,
  }),
}));
```

### Selections across an interface

- An object's selection includes the `select` of every interface it implements. Its own fields can
  read what the interface selects, like the interface's fields can.
- A row loaded as the interface also loads the columns that every implementing object's `select`
  lists, whether or not the query has a `... on Type` fragment. The to-many relations and
  function-form values in an object's `select` load with it too. So `isTypeOf`, a type-level
  `authScopes` and the object's fields see them.
- A to-one relation in an object's `select` loads only under a `... on Type` fragment. Otherwise
  the object's fields reload the row to get it. Relations declared on a variant work the same way.
- When an interface's `select` and the object's `select` load the same to-one relation with
  different arguments, the interface's columns still load with the object. The interface's
  relation loads separately, for the fields the interface declares.

Add fields with `prismaInterfaceField` or `prismaInterfaceFields`, passing the ref:

```ts
builder.prismaInterfaceField(Person, 'displayName', (t) =>
  t.string({
    select: ['firstName', 'lastName'],
    resolve: (person) => `${person.firstName} ${person.lastName}`,
  }),
);
```

Interfaces accept `variant` like objects do.

## Native inheritance

A base model with variants in the contract maps to an interface, with an object for each variant.
The interface selects the discriminator and resolves each row to its variant's type:

```ts
const task = builder.prismaInterface('Task', {
  fields: (t) => ({
    id: t.exposeID('id'),
    owner: t.relation('owner'),
  }),
});

builder.prismaObject('Bug', {
  interfaces: [task],
  fields: (t) => ({
    severity: t.exposeString('severity'),
  }),
});

builder.queryType({
  fields: (t) => ({
    tasks: t.prismaField({
      type: [task],
      resolve: (_root, _args, ctx) => ctx.db.orm.Task,
    }),
    bugs: t.prismaField({
      type: ['Bug'],
      resolve: (_root, _args, ctx) => ctx.db.orm.Task.variant('bug'),
    }),
  }),
});
```

- Return a variant type from `orm.Base.variant(value)`. `orm.Bug` isn't filtered by Prisma, so it
  is rejected.
- Each variant needs exactly one implementing type, unless the interface has a `resolveType`.
- `prismaNode` works on a variant, and loads it through `orm.Task.variant('feature')`.
- A relation declared on a variant loads under `... on Bug` in a separate batched query.
- `t.relation` and `t.relatedConnection` with a variant `type` only return, and count, that
  variant's rows.
- The relations a variant inherits load in a separate batched query when a relation targets the
  variant model.
