---
title: Interfaces
description: GraphQL interfaces backed by contract models
---

`builder.prismaInterface` takes the same options as `builder.prismaObject` and creates an
interface. Objects implementing it must use the same model, or one of its
[variant models](#native-inheritance). Give the interface a `resolveType`, and list the columns it
reads in the interface's `select`:

```ts
const Person = builder.prismaInterface('User', {
  variant: 'Person',
  select: ['email'],
  resolveType: (user) => (user.email.endsWith('@admin.example.com') ? 'Admin' : 'User'),
  fields: (t) => ({
    id: t.exposeID('id'),
    firstName: t.exposeString('firstName'),
  }),
});

builder.prismaObject('User', {
  interfaces: [Person],
  fields: (t) => ({
    email: t.exposeString('email'),
  }),
});

builder.prismaObject('User', {
  variant: 'Admin',
  interfaces: [Person],
  fields: (t) => ({
    email: t.exposeString('email'),
  }),
});

builder.queryFields((t) => ({
  people: t.prismaField({
    type: [Person],
    resolve: (_root, _args, ctx) => ctx.db.orm.User,
  }),
}));
```

`t.prismaField`, `t.prismaConnection`, `t.relation` and `t.relatedConnection` all accept an
interface ref as `type`. Objects don't take `isTypeOf`.

An implementation's fields can read the interface's `select`, and rows loaded through the interface
also load each implementation's type-level `select`.

To return a row through `Node` or an interface from `builder.interfaceRef()`, brand it with the
type's `addBrand`, such as `User.addBrand(row)`. Unbranded rows fail with
`Abstract type ... must resolve`. Routing a row by hand with `__typename` or a `resolveType` that
returns a type name skips `addBrand`'s check that the row has the type's key and `select`.

Add fields with `prismaInterfaceField` or `prismaInterfaceFields`:

```ts
builder.prismaInterfaceField(Person, 'displayName', (t) =>
  t.string({
    select: ['firstName', 'lastName'],
    resolve: (person) => `${person.firstName} ${person.lastName}`,
  }),
);
```

## Native inheritance

A base model with variant models in the contract maps to an interface, with an object for each
variant. Rows resolve to their variant's type by the discriminator, so no `resolveType` is needed:

```ts
const task = builder.prismaInterface('Task', {
  fields: (t) => ({
    id: t.exposeID('id'),
    owner: t.relation('owner'),
  }),
});

builder.prismaObject('Bug', {
  interfaces: [task],
  fields: (t) => ({
    severity: t.exposeString('severity'),
  }),
});

builder.queryType({
  fields: (t) => ({
    tasks: t.prismaField({
      type: [task],
      resolve: (_root, _args, ctx) => ctx.db.orm.Task,
    }),
    bugs: t.prismaField({
      type: ['Bug'],
      resolve: (_root, _args, ctx) => ctx.db.orm.Task.variant('bug'),
    }),
  }),
});
```

- Return a variant's rows from `orm.Base.variant(value)`, not `orm.Bug`, which Prisma doesn't
  filter by the discriminator.
- Each variant needs exactly one implementing type, unless the interface has a `resolveType`.
- A relation declared on a variant can't be in the variant type's `select`. Use a field's `select`
  or `t.relation`.
- A relation name declared by more than one variant can't be loaded.
- Pass a variant's ref as `type` to `t.relation` or `t.relatedConnection` to return only that
  variant's rows.
- A row returned from a plain `t.field` needs the interface's `select` and the discriminator.
