---
title: Interfaces
description: GraphQL interfaces backed by contract models
---

`builder.prismaInterface` takes the same options as `builder.prismaObject` and creates an
interface. Objects implementing it must use the same model:

```ts
const Person = builder.prismaInterface('User', {
  name: 'Person',
  fields: (t) => ({
    id: t.exposeID('id'),
    firstName: t.exposeString('firstName'),
  }),
});

builder.prismaObject('User', {
  interfaces: [Person],
  select: ['email'],
  isTypeOf: (user) => !user.email.endsWith('@admin.example.com'),
  fields: (t) => ({
    email: t.exposeString('email'),
  }),
});
```

`t.prismaField` and `t.prismaConnection` take an interface ref as `type`. A relation returns an
interface when its target model is registered with `prismaInterface`, as in
[Native inheritance](#native-inheritance).

Give the implementations an `isTypeOf`, or the interface a `resolveType`. List the columns an
`isTypeOf` reads in that object's `select`, and the columns a `resolveType` reads in the
interface's `select`:

```ts
builder.prismaObject('User', {
  variant: 'Admin',
  interfaces: [Person],
  select: ['email'],
  isTypeOf: (user) => user.email.endsWith('@admin.example.com'),
  fields: (t) => ({
    email: t.exposeString('email'),
  }),
});

builder.queryFields((t) => ({
  people: t.prismaField({
    type: [Person],
    resolve: (_root, _args, ctx) => ctx.db.orm.User,
  }),
}));
```

Add fields with `prismaInterfaceField` or `prismaInterfaceFields`, passing the ref:

```ts
builder.prismaInterfaceField(Person, 'displayName', (t) =>
  t.string({
    select: ['firstName', 'lastName'],
    resolve: (person) => `${person.firstName} ${person.lastName}`,
  }),
);
```

Interfaces accept `variant` like objects do.

## Selections

An object's fields can read its interfaces' `select`. A row loaded through the interface also
loads each implementation's `select`, so `isTypeOf` and type-level `authScopes` can read it
without a `... on Type` fragment (see [With scope-auth](./setup#with-scope-auth) for plugin order).
Implementations that load the same to-one relation with different arguments fail the schema build.

## Native inheritance

A base model with variants in the contract maps to an interface, with an object for each variant.
The interface selects the discriminator and resolves each row to its variant's type:

```ts
const task = builder.prismaInterface('Task', {
  fields: (t) => ({
    id: t.exposeID('id'),
    owner: t.relation('owner'),
  }),
});

builder.prismaObject('Bug', {
  interfaces: [task],
  fields: (t) => ({
    severity: t.exposeString('severity'),
  }),
});

builder.queryType({
  fields: (t) => ({
    tasks: t.prismaField({
      type: [task],
      resolve: (_root, _args, ctx) => ctx.db.orm.Task,
    }),
    bugs: t.prismaField({
      type: ['Bug'],
      resolve: (_root, _args, ctx) => ctx.db.orm.Task.variant('bug'),
    }),
  }),
});
```

- Return a variant type from `orm.Base.variant(value)`. `orm.Bug` isn't filtered by Prisma, so it
  is rejected.
- Each variant needs exactly one implementing type, unless the interface has a `resolveType`.
- `prismaNode` works on a variant, and loads it through `orm.Task.variant('bug')`.
- `t.relation` and `t.relatedConnection` with `type` set to the ref of a variant model's object,
  such as `Bug`, only return, and count, that variant's rows. Such a to-one relation is nullable.
