---
title: Indirect relations
description: Loading relations for fields that aren't t.relation
---

A field's `select` function gets a third argument, `nestedSelection`. Use it as a relation's entry,
and the relation's rows load with what the query selects on the field's type, in the parent's
query:

```ts
const Post = builder.prismaObject('Post', {
  fields: (t) => ({ title: t.exposeString('title') }),
});

builder.prismaObject('User', {
  fields: (t) => ({
    publishedPosts: t.field({
      type: [Post],
      select: (args, ctx, nestedSelection) => ({
        posts: nestedSelection({ where: { published: 1 } }),
      }),
      resolve: (user) => user.posts,
    }),
  }),
});
```

Without it, `{ posts: true }` loads each post's columns but nothing the query selects beneath the
field, such as `author`, which then loads in an extra batched statement. Use `nestedSelection`
whenever the field's type has relations or selects of its own, so they load in the parent's query.

`nestedSelection` takes three optional arguments:

- `query`: what a relation's [`query`](./relations#filtering-and-sorting) takes. A to-one relation
  takes none.
- `path`: a field nested under the field's type to read the selection from. A segment can be
  written as `{ name, type }` to only read the field under a fragment on that type.
- `type`: the type to read the selection as, when the field returns an interface or union. It
  takes what a field's `type` takes, or a model's name for its default type. The query and rows are
  typed by that type's model, which must be the relation's target.

The rows hold the primary key and what the selection loads, not every column.

## Selecting fields from a nested GraphQL field

When the field returns a type without a model, pass the `path` of a field beneath it that returns
the model's type:

```ts
const PostPreview = builder.objectRef<typeof Post.$inferType>('PostPreview').implement({
  fields: (t) => ({
    post: t.field({ type: Post, resolve: (post) => post }),
  }),
});

builder.prismaObject('User', {
  fields: (t) => ({
    postPreviews: t.field({
      type: [PostPreview],
      select: (args, ctx, nestedSelection) => ({
        // What the query selects under `postPreviews.post`, for the 2 newest posts
        posts: nestedSelection({ orderBy: { createdAt: 'desc' }, limit: 2 }, ['post']),
      }),
      resolve: (user) => user.posts,
    }),
  }),
});
```

## Selecting as a specific type

When the field returns an interface or union, `type` names the object type to read the selection
as. Fragments on other types are left out:

```ts
const Comment = builder.prismaObject('Comment', {
  fields: (t) => ({ body: t.exposeString('body') }),
});

const Activity = builder.unionType('Activity', {
  types: [Post, Comment],
  resolveType: (row) => ('title' in row ? 'Post' : 'Comment'),
});

builder.prismaObject('User', {
  fields: (t) => ({
    recentActivity: t.field({
      type: [Activity],
      select: (args, ctx, nestedSelection) => ({
        posts: nestedSelection({ limit: 5 }, [], Post),
        comments: nestedSelection({ limit: 5 }, [], Comment),
      }),
      resolve: (user) => [...user.posts, ...user.comments],
    }),
  }),
});
```

## Join models

A relation defined with `rel.manyToMany` loads through its junction table, so `nestedSelection` and
`t.relation` work on it like any to-many relation.

For a join model of its own, give the relation entry a `select` of the join model's rows and put
`nestedSelection` beneath it. Here comments join users to the posts they commented on:

```ts
builder.prismaObject('User', {
  fields: (t) => ({
    commentedPosts: t.field({
      type: [Post],
      select: (args, ctx, nestedSelection) => ({
        comments: {
          query: { orderBy: { createdAt: 'desc' } },
          select: { post: nestedSelection() },
        },
      }),
      resolve: (user) => user.comments.map((comment) => comment.post),
    }),
  }),
});
```

The `select` takes the same entries as any other, one level down, and everything loads in the
parent's query.
