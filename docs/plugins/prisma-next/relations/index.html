Relations

Adding relations to Prisma-backed types

Use t.relation to expose a relation from your contract as a field. The plugin loads it with the parent's query, so a user's posts come back with the user:

Relation fields use the builder's default field nullability, whether or not the relation is optional in the contract. Pass nullable to override.

Nullable relations and onNull

A to-one relation can be null when it is optional in the contract, or when a variant type filters the row out. To expose one as a non-null field, you have to set onNull. 'error' makes GraphQL raise its usual non-null error for the field. A function can return an Error to throw instead, or a replacement row loaded with collectionFromInfo. Filtering and sorting

Pass query to filter, sort, or limit the related rows. It takes { where, orderBy, limit, offset }, or a function of the field's arguments and context that returns one. where takes anything the Collection's where() does. orderBy takes columns, each with a direction, and sorts nulls last unless you set nulls, as in a connection. Counts and other aggregates

t.relationCount adds an Int field that counts a to-many relation. Pass a query with a where to count only some rows:

query works as it does on t.relation, but only takes where. where can also be a predicate: query: { where: (post) => post.published.eq(1) }.

Count fields are always non-null. If an auth check on one fails, GraphQL sets the parent to null instead. To hide a count from some users, use a nullable field with a select, as below.

For sums and other aggregates, use a function for the relation in a field's select. It gets the relation's Collection and returns an object of aggregates. Each key is added to the parent row:

Aggregate functions shouldn't have side effects.

Many-to-many

Relations defined with rel.manyToMany({ through, from, to }) work with t.relation. To expose columns from the junction table, define the junction as its own model and use two relations.

Returning rows from other fields

A plain t.field that returns a model's type has to return rows loaded by the plugin: the parent, relation rows loaded by a select, or rows from a query built with collectionFromInfo. These rows are typed as PrismaPlanned<'User'>. Returning a row you built by hand or loaded with a plain ORM query is a type error.

To load a relation as one of its variants, set type to the variant's ref or model name. Only that variant's rows are loaded:

collectionFromInfo loads everything the query selects under the field, including relations and counts, in one query, like a t.prismaField. See Mutations for its path and typeName options:

In a subscription, call it in resolve, which runs for each event. Rows returned from subscribe are loaded again.

To return a row from a field whose type is Node or an interface from builder.interfaceRef():

  • Brand it with the type's addBrand, such as User.addBrand(row). Rows without a brand fail with Abstract type ... must resolve.
  • If you set __typename yourself, or use a resolveType that returns a type name, TypeScript doesn't check that the row was loaded by the plugin.
