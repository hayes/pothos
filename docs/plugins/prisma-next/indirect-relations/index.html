Indirect relations

Loading relations for fields that aren't t.relation

Use t.relation for a direct relation, including a renamed or filtered field. Use t.field with a select when the field goes through a join model, wraps the rows in another GraphQL type, or needs its own resolver logic.

A field's select function gets nestedSelection as its third argument. Use it as the value for a relation, and the plugin loads that relation in the parent's query, with whatever the client selects on the field's type:

For this filtered field alone, prefer publishedPosts: t.relation('posts', { query: { where: { published: 1 } } }).

With { posts: true } instead, the plugin only loads each post's columns. Anything selected under the field, such as a post's author, needs an extra batched query. Use nestedSelection whenever the field's type has relations or selects of its own.

nestedSelection takes an optional object with the same options as a relation entry, plus path:

  • where, orderBy, limit, offset: the relation's query options. A to-one relation takes none.
  • select: anything else to load for each row, on top of what the query selects.
  • path: the path to a nested field to read the selection from. A segment can be written as { name, type } to only read the field inside a fragment on that type.
  • type: the type to read the selection as, when the field returns an interface or union. You can pass anything a field's type takes, or a model's name for its default type. The type's model must be the relation's target, and the query and rows are typed for that model.

The rows only include the primary key and the selected columns, not every column.
