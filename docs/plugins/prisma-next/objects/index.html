Objects

Defining GraphQL types backed by contract models

builder.prismaObject defines a GraphQL object type for a model in your contract.

Define a type

Pass the model name and the usual object type options. Column types come from the contract.

The GraphQL type is named after the model. Pass name to call it something else.

To add fields to a type elsewhere, use prismaObjectFields. To expose the same model as another GraphQL type, define a variant or a prismaInterface. To return these objects from a query field, use t.prismaField; see Queries and selections.

Selections

Use select when a resolver needs columns or relations that the field doesn't expose. The plugin loads them with the rest of the query:

A select accepts:

  • Columns: { email: true } or ['email'].
  • Relations: { posts: true }, which loads the relation's scalar columns.
  • Filtered or sorted relations: { posts: { where: { published: 1 }, orderBy: { createdAt: 'desc' }, limit: 5 } }. where and orderBy take the same values as in t.relation's query.
  • A nested select for the relation's rows: { comments: { limit: 5, select: { post: true } } }.
  • type: a ref or model name for a variant of the related model. Only that variant's rows are loaded: { tasks: { type: Bug } }.
  • Counts and aggregates of a to-many relation, in a field's select only: { posts: (posts) => ({ postCount: posts.count() }) }. Each key (postCount) is added to the row, so don't use the name of a column or relation.

A to-one relation only takes type and select. Aggregates have to be read in a resolver, because t.expose* only works on columns.

A model's types (the object, its variants and interfaces) can each have a select. If two of them select the same relation, they have to use the same options, including in nested selects, or the schema build throws. where and orderBy functions are compared by reference, so share one function between the types. To load a relation with different options, use t.relation or a field's select.

A field's select can also be a function of its arguments and context. Here the field selects lastName only when the client asks for the full name. A column that only some branches select is optional on the parent:

With AsyncSelections: true in the builder's types, the function can be async.

The function's third argument, nestedSelection, is for custom fields that return objects. Use it for a relation to load what the query selects under the field. The rows only include the primary key and the selected columns, so pass it a select for anything else the resolver reads. See Indirect relations for examples.

select, query and where functions are called while the plugin builds a query, not once per row. They can be called more than once in a request, so they shouldn't have side effects.

Resolver data

A resolver can read the model's primary or non-null unique key, the type's select, and its own field's select. Other columns may not be loaded.

The type of a row loaded by the plugin includes PrismaPlanned<'User'>. To return rows from custom resolvers, see Returning rows from other fields.

Auth checks

Auth checks on the type, and field options from other plugins such as authScopes and grantScopes, can read:

  • the primary key
  • the columns and relations in the selects of the type and its interfaces
  • on a t.expose* field, the exposed column

A field's own select is only available in resolve. If a row is missing any of these, the plugin reloads it by its key before the check.

If the payload field is an interface or union, pass typeName to choose the GraphQL object type to load. For mutations on inherited models, see Model inheritance.

If you export a function that returns rows from collectionFromInfo, give it a return type such as Promise<PrismaPlanned<'User'> | null> so TypeScript can emit its declaration.

Adding fields

To add fields to a type from another file, use prismaObjectField or prismaObjectFields. builder.objectField won't work here because it doesn't support select.

If the resolver reads the type's select, pass the ref that prismaObject returns instead of the model name. Passing a variant's ref adds fields to that variant.
