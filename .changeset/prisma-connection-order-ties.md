`relatedConnection` and `prismaConnectionHelpers` connections whose `orderBy` is not unique now add the cursor's fields as a final sort key, in the direction of the last `orderBy` entry, so pages read backward with `last` match the pages read forward. This changes forward pages too: rows that tie on the `orderBy` used to come back in whatever order the database chose and now come back in cursor order, and the query has one more sort column. Pages from a cursor over such an order are now paged in SQL rather than in memory, which is much faster for most pages; an index that ends with the cursor key (for example `(authorId, postId, id)`) keeps them fast. A cursor issued before upgrading continues in the new order, so a client paging through tied rows across the upgrade can see a row twice or miss one. To choose the order of tied rows yourself, end `orderBy` with a unique, non-null column; an `orderBy` that is absent or already unique is passed through unchanged. For a non-unique order, the `orderBy` returned by a connection helper's `getQuery` is now an array, and its type is now `OrderBy | OrderBy[]`: code that reads it as a single object (for example `getQuery(...).orderBy?.createdAt`) no longer compiles and needs to handle both forms. `first` together with `last` now pages forward by `first`, as `@pothos/core` does.
